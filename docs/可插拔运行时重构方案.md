# di-code 可插拔运行时重构方案

状态：提案（实现前设计基线）
适用版本：`di-code` 下一次主版本重构
参考实现：`D:\pi\deepseek-harness-master` 的 Cordis/Loader 组合运行时

## 1. 目标和结论

当前 `di-code` 的 `plugins`/`extensions` 是“宿主已经完成主要工作，插件只能追加工具、命令和事件监听器”的扩展 API。Provider、Agent loop、工具、Session、压缩、CLI mode、TUI、RPC、MCP、Skills 和 orchestrator 仍由 `coding-agent` 直接 import、`new` 和硬编码组装，因此不能满足“一切皆插件”。

本次工作应在当前项目上做架构级重构，而不是继续扩大旧 API：

1. 删除 `packages/coding-agent/src/plugins`、`packages/coding-agent/src/extensions`、`ExtensionHost`、旧 manifest/factory 入口和兼容 re-export；最终不保留双轨运行时。
2. 新增独立的 `@di-code/plugin-runtime`、`@di-code/plugin-loader`、`@di-code/plugin-sdk`。
3. 采用 dsh 的核心模型：`Context + Fiber + Service + Event + Loader + Composition`。
4. Provider、Agent、工具、Session、CLI/TUI、RPC、MCP、Skills 等全部以 plugin entry 组装；默认体验只是可复现的 profile，而不是宿主里的隐藏分支。
5. 以真实 Loader/CLI/RPC 组合测试作为最终证据。手工 `ctx.plugin(...)` 测试只能覆盖 runtime 单元行为，不能单独证明产品可插拔。

本方案定义的“完全可插拔”是可验证合同：

- 业务功能的唯一运行时入口是插件服务、贡献注册表或 typed event；宿主不直接 import 该功能实现。
- 删除/禁用可选 entry 后，其他 entry 仍可启动；缺少的能力只能产生明确诊断或有界的 `unavailable` 结果。
- 卸载/reload 后，插件拥有的服务、工具、命令、监听器、Provider、资源、进程、文件句柄和定时器全部释放；重复加载不会重复贡献。
- 插件可以挂在 Root、Project、Session、Agent、Request、Turn、ToolCall scope；Session 私有服务不得泄漏到 Root，两个 Session 不得互相可见。
- 外部 npm/local plugin 只依赖公开 SDK 和组合配置，不依赖 `coding-agent/src`、其他包的 `src`/`dist` 私有路径。
- 每个用户可见插件都有真实组合测试、移除测试和外部 fixture plugin smoke test。

## 2. 当前基线和 dsh 借鉴范围

### 2.1 当前硬编码点

| 现状位置 | 当前行为 | 目标归属 |
| --- | --- | --- |
| `AgentSession` | 直接创建七类内建工具和外部工具 | `tool-*` plugins -> `ToolRegistry` |
| `main.ts` | 直接选择 Provider、加载 MCP、构造资源、Session、mode | Bootstrap + Loader；其余能力由 plugins 提供 |
| `buildSystemPrompt` | 直接拼接系统提示 | `PromptSectionRegistry` |
| `ExtensionHost` | 独立保存 tools/commands/handlers | 删除；统一 Runtime Registry/EventBus |
| `plugins/loader.ts` | 只加载工厂并挂到 Host | 删除；由声明式 Loader 管理 Entry Tree/Fiber |
| `rpc-entry.ts` | 直接构造 AgentSession/RPC server | `rpc-server` plugin + `SessionFactoryRegistry` |
| `mcp/loader.ts` | 启动流程专用分支 | `mcp-config`、`mcp-client`、`mcp-tools` plugins |
| `orchestrator` | 假设固定 RPC 入口 | 只依赖公开 RPC 协议/SDK |

实现前应继续以以下文件为行为基线：根 `README.md`、`docs/插件使用指南.md`、`docs/开发教程.md`、`packages/coding-agent/src/{main,entry,rpc-entry}.ts`、`src/core/session.ts`、`src/core/tools/*`、`src/plugins/*`、`src/extensions/*`、`packages/agent`、`packages/ai`、`packages/mcp`、`packages/orchestrator` 及其测试。

### 2.2 dsh 必须借鉴的机制

- `Context` 是服务和事件的访问边界；子 Context 继承父 Context，并可用 isolate realm 隔离 Session。
- `Fiber` 是插件实例生命周期；effect/disposer 归属 Fiber，状态包含 pending/loading/active/failed/unloading/disposed。
- 插件用 namespace export 提供 `name`、`inject`、`Config`、`apply`；Loader 在导入后校验元数据，发布插件禁止 `default` export。
- `Loader` 维护声明式 Entry Tree，支持 group/disabled/include/patch，按依赖挂载和卸载。
- Registry 记录贡献 owner；Fiber unload 自动撤销，inventory 直接投影 Loader 当前状态，不维护第二套生命周期真相。
- 异步 import 或 handler 完成时必须检查 Fiber 仍 active，防止卸载后的迟到注册。
- 用户可见插件必须通过真实 Loader/Composition 启动测试。

不直接复制 dsh 的 Web、Remote、Typert、profile 命名和业务实现；`di-code` 继续使用自己的 Provider-neutral AI 协议、Session JSONL、ANSI TUI 和 RPC v1。

## 3. 目标架构和包边界

### 3.1 依赖方向

```text
@di-code/ai
      ^
@di-code/agent
      ^
@di-code/plugin-runtime
      ^
@di-code/plugin-loader
      ^
@di-code/plugin-sdk
      ^
@di-code/coding-agent (Bootstrap + default compositions)
      ^                 ^
@di-code/orchestrator --+  (公开 RPC SDK/协议)
```

推荐 workspace：

```text
packages/
  plugin-runtime/       @di-code/plugin-runtime
  plugin-loader/        @di-code/plugin-loader
  plugin-sdk/            @di-code/plugin-sdk
  plugin-contract-tests/ private fixture helpers
  coding-agent/          Bootstrap/bin/profile files
  builtins/              plugin-provider-*, plugin-tool-*, plugin-session-*, ...
```

当前根 `package.json` 只有 `packages/*` workspace；实现时必须显式覆盖 `packages/builtins/*`，或者让每个 built-in 作为直接 workspace。不能把所有实现留在 `coding-agent/src` 后仅添加一个“大工厂”并称为插件。

### 3.2 Runtime 层次

```text
RootContext
  - Bootstrap / Loader / Trust / Diagnostics / Inventory / Exit
  - ProviderRegistry / AgentRegistry / SessionFactoryRegistry
  - CLI/TUI/RPC host services
  - ProjectContext (trusted project composition)
      - SessionContext #1 (isolated)
          - AgentContext -> RequestContext -> TurnContext -> ToolCallContext
      - SessionContext #2 (isolated)
```

规则：Root 只放进程基础设施；Project 只放配置/信任；Session/Agent 私有贡献必须在 isolate realm；短生命周期 Context 只携带可取消 signal 和 tracing metadata。子 Context 先于父 Context dispose。

### 3.3 Bootstrap 最小职责

最终 `coding-agent/src/main.ts` 只允许：

1. 解析 `--help`、`--version`、`--profile`、`--composition`、`--no-project-plugins`、`--trace-plugins`。
2. 创建 RootContext、root `AbortController`。
3. 挂载 Runtime、Loader、Diagnostics、Trust、Exit 五个 Bootstrap plugin。
4. 解析并加载 profile/composition，等待 required entries settled。
5. 从 `HostCommandRegistry` 找到命令并执行。
6. 反向 dispose 并映射稳定退出码。

Bootstrap 不得直接 import Provider adapter、Agent、Session、工具、MCP、TUI component、slash command、压缩算法或 RPC method。

## 4. 核心公共协议

### 4.1 PluginDefinition

公共类型位于 `@di-code/plugin-runtime`，由 `@di-code/plugin-sdk` 根入口重新导出：

```ts
export const PLUGIN_API_VERSION = 1 as const;

export interface PluginDefinition<TConfig = unknown> {
  readonly apiVersion: typeof PLUGIN_API_VERSION;
  readonly name: string;
  readonly version: string;
  readonly inject?: readonly ServiceKey[];
  readonly optionalInject?: readonly ServiceKey[];
  readonly Config?: ConfigSchema<TConfig>;
  readonly capabilities?: PluginCapabilities;
  readonly apply: (ctx: Context, config: TConfig) => void | Promise<void>;
}

export interface PluginCapabilities {
  readonly filesystem?: 'none' | 'workspace' | 'user' | 'unrestricted';
  readonly network?: readonly string[];
  readonly process?: readonly string[];
  readonly ui?: readonly ('terminal' | 'overlay' | 'raw-ansi')[];
  readonly credentials?: readonly string[];
}
```

发布插件使用 namespace export：

```ts
export const apiVersion = 1 as const;
export const name = 'tool-read';
export const version = '1.0.0';
export const inject = ['tools', 'workspace'] as const;
export const Config = configSchema;
export async function apply(ctx: Context, config: Config): Promise<void> { /* ... */ }
```

规则：`name` 使用安全字符；一个 module 代表一个逻辑 plugin；多能力使用 package subpath；`definePlugin()` 只做类型推导，不能跳过 Loader 验证；发布 namespace 中出现 `default` 必须拒绝。

### 4.2 Context、Service、Fiber

```ts
export type ServiceKey<T = unknown> = string & { readonly __serviceType?: T };

export interface Context {
  readonly root: Context;
  readonly parent?: Context;
  readonly fiber: Fiber;
  readonly cwd: string;
  readonly mode: RuntimeMode;
  readonly baseUrl: string;
  readonly signal: AbortSignal;
  readonly services: ServiceRegistry;
  readonly events: EventBus;
  readonly logger: PluginLogger;
  readonly capabilities: CapabilityView;
  get<T>(key: ServiceKey<T>): T | undefined;
  require<T>(key: ServiceKey<T>): T;
  provide<T>(key: ServiceKey<T>, value: T, options?: ProvideOptions): Disposer;
  plugin<TConfig>(definition: PluginDefinition<TConfig>, config?: TConfig): Promise<Fiber>;
  effect(disposer: Disposer, label?: string): void;
  child(options: ChildContextOptions): Context;
}

export type FiberPhase = 'pending' | 'loading' | 'active' | 'failed' | 'unloading' | 'disposed';
```

`provide` 返回精确 disposer；默认重复 provide 报冲突；Fiber active 前不发布服务；apply 失败必须回滚；dispose 幂等、abort 后等待 in-flight 任务，再逆序执行 disposer；disposer 错误聚合但不能阻止其他清理。Registry record 必须保存 owner Fiber、scope 和创建时间。

### 4.3 注入和启动顺序

`inject` 是必需服务，`optionalInject` 是可选服务。Loader 必须：

1. 校验 entry id、plugin name、版本、config 和 capability。
2. 展开 group/include/patch，保留配置来源。
3. 对必需依赖做拓扑排序，拒绝循环、缺失和重复 owner。
4. 先发布 provider，再激活消费者；不能用无限重试隐藏缺失依赖。
5. optional service 缺失时允许 active，但 plugin 必须显式处理 `undefined`。
6. 同优先级并行 entry 按稳定 entry id 排序；需要顺序时用显式依赖。

### 4.4 EventBus

事件必须使用 discriminant、关联 id 和可序列化 payload：

```ts
export type RuntimeEvent =
  | { readonly type: 'runtime_start'; readonly runId: string }
  | { readonly type: 'plugin_status'; readonly status: PluginStatus }
  | { readonly type: 'session_start'; readonly sessionId: string }
  | { readonly type: 'turn_start'; readonly sessionId: string; readonly turnId: string }
  | { readonly type: 'model_request'; readonly requestId: string; readonly model: string }
  | { readonly type: 'tool_call_start'; readonly toolCallId: string; readonly name: string }
  | { readonly type: 'tool_call_end'; readonly toolCallId: string; readonly ok: boolean }
  | { readonly type: 'session_event'; readonly event: AgentSessionEvent }
  | { readonly type: 'session_shutdown'; readonly sessionId: string; readonly reason: ShutdownReason };
```

observer handler 默认隔离错误并记录诊断；critical gate 才能阻止后续阶段，且必须有 timeout/abort。handler 隶属于订阅 Fiber，Fiber unload 自动 unsubscribe。Agent loop 仍只有 `@di-code/agent` 一套，事件不是第二套 loop。

### 4.5 Contribution Registry

统一 owner/disposer 语义：

```ts
export interface ContributionRegistry<T> {
  register(value: T, options: ContributionOptions): Disposer;
  list(filter?: ContributionFilter): readonly OwnedContribution<T>[];
  snapshot(): readonly T[];
}
```

必须有：

| Registry | 用途 |
| --- | --- |
| `ProviderRegistry` | Provider、模型目录、factory、credential resolver |
| `ToolRegistry` | schema、execute、presentation、capability |
| `CommandRegistry` | CLI/slash command、参数解析、handler、mode |
| `PromptSectionRegistry` | 系统提示 section、顺序、scope、cache |
| `SessionStoreRegistry` | create/open/append/load/compact/query |
| `SessionFactoryRegistry` | Session/Agent factory 和 scope |
| `CompactionRegistry` | estimate/shouldCompact/compact |
| `OutputRendererRegistry` | print/json/interactive event renderer |
| `RpcMethodRegistry` | method、schema、handler、permission |
| `ResourceRegistry` | Skills、images、system files、provenance |
| `Theme/KeybindingRegistry` | TUI theme、按键、overlay |
| `McpTransportRegistry` | transport connect/list/call/close |
| `DiagnosticSinkRegistry` | redaction、stderr/log/RPC sink |

每个 Registry 都提供只读 inventory，禁止产品模块维护第二个数组或生命周期缓存。

## 5. 声明式 Composition 和插件包

### 5.1 配置层次

```text
packages/coding-agent/compositions/base.yml
packages/coding-agent/compositions/interactive.yml
packages/coding-agent/compositions/print.yml
packages/coding-agent/compositions/json.yml
packages/coding-agent/compositions/rpc.yml
.di-code/composition.yml
~/.di-code/composition.yml
```

最终顺序固定为：`base -> mode -> user -> project -> explicit --composition`。后层通过 patch 修改前层，不允许插件私自读配置并暗改树。

### 5.2 Entry 结构

```yaml
- id: tool-read
  name: '@di-code/plugin-tool-read'
  config:
    maxBytes: 200000
  inject: [tools, workspace]
  capabilities:
    filesystem: workspace

- id: optional-mcp
  name: '@di-code/plugin-mcp-client'
  disabled: true
```

规范：entry `id` 在最终树唯一；同一 package 多次挂载必须明确 scope/config；`config` 只接受 JSON/YAML 和受限环境变量；禁止任意 eval、命令替换、shell 字符串；disabled entry 不 import、不连接、不提供服务；group 只组织树；patch 支持 `insert/append/remove/replace/enable/disable/move`，目标必须是明确 id。required failure 阻止启动，optional failure 隔离并诊断。

### 5.3 package manifest 和 exports

```json
{
  "name": "@di-code/plugin-tool-read",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js" },
    "./plugin": { "types": "./dist/plugin.d.ts", "import": "./dist/plugin.js" }
  },
  "diCode": { "apiVersion": 1, "plugins": ["./plugin"] }
}
```

Loader 必须验证 api major、plugins 数组、包内 export 边界、namespace `apply/name/version` 和无 default。显式 required package 解析失败要 fail-fast；自动发现的可选贡献可以 skipped，但必须诊断。

### 5.4 安装和管理

`plugin-manager` 可以保留安装能力，但它必须作为 plugin 工作：

- 只写 `~/.di-code/plugins/installed/<safe-id>`；`resolve + relative` 验证 managed path。
- npm 使用 `--ignore-scripts`；git 使用固定参数和 staging；失败时清理 staging，旧版本可回滚。
- registry 版本化 JSON，临时文件 + rename，并发追加受锁保护。
- enable/disable 只改变组合/registry，不 import disabled plugin。
- remove 只能删除 managed install root 下已注册目录。
- in-process plugin 拥有 Node 进程权限；manifest capability 是审计和运行时门禁，不是沙箱。真正不可信代码另行使用 `isolated-process` bridge，不能在文档中宣称 in-process 安全隔离。

## 6. 内建功能插件化蓝图

### 6.1 Bootstrap/基础设施

`runtime-core`、`composition-loader`、`project-trust`、`diagnostics`、`plugin-inventory`、`plugin-manager`、`process-exit`。宿主只直接挂载前五类 Bootstrap；管理命令自身也来自 CommandRegistry。

### 6.2 Provider、模型、凭据

`provider-registry`、`provider-openai`、`provider-anthropic`、`provider-deepseek`、`provider-kimi`、`provider-zhipu`、`provider-faux`、`model-catalog`、`credential-env`、`provider-onboarding`、`runtime-selection`。

Provider 只能使用 `@di-code/ai` 的统一 Message/Provider/Event 类型；厂商字段不能泄漏进 Agent 公共类型。缺 Provider 只影响选择它的 profile；faux 必须可离线运行。

### 6.3 Agent、Session、上下文

`agent-loop`、`agent-session`、`session-store-jsonl`、`session-tree`、`session-query`、`session-migrations`、`usage-meter`、`context-budget`、`compaction-basic`、`compaction-tool-result`、`system-prompt`、`resource-loader`、`skills`。

`@di-code/agent` 保持纯 Provider-neutral loop engine；`agent-loop` plugin 才把 engine 与 Product Registry 组装。`AgentSession` 不再创建工具数组。

### 6.4 工具和策略

`workspace`、`tool-read`、`tool-write`、`tool-edit`、`tool-bash`、`tool-glob`、`tool-grep`、`tool-load-skill`、`tool-approval`、`tool-policy`、`tool-output`。

每个工具通过 `ToolRegistry` 注册；Agent loop 不认识工具名单。路径 realpath/symlink、结构化 spawn、timeout、输出上限、取消和 mutation queue 仍由工具/能力服务负责。

### 6.5 CLI、TUI、输出

`cli-parser`、`command-core`、`command-session`、`command-model`、`command-settings`、`command-compact`、`mode-interactive`、`mode-print`、`mode-json`、`mode-rpc`、`tui-renderer`、`tui-theme`、`output-json`。

帮助文本从 CommandRegistry 生成；mode 是组合 entry，不是 `main.ts` 的业务 if/else；TUI 仍只负责 presentation。

### 6.6 MCP、RPC、orchestrator

`mcp-config`、`mcp-client`、`mcp-tools`、`rpc-protocol-v1`、`rpc-server`、`rpc-events`、`rpc-client-sdk`、`orchestrator-host`。

RPC 保留 `version: 1`、`id`、`requestId` 和现有错误码；新 method 必须进入 namespace `RpcMethodRegistry`。MCP 只是 `ToolRegistry` 的贡献源，不得实现第二套 Agent loop。orchestrator 只依赖公开 RPC。

### 6.7 观测和开发插件

`plugin-trace`、`plugin-profiler`、`plugin-invariants`、`plugin-test-runtime`、`plugin-dump-composition` 只进入开发/测试 profile，不进入默认生产组合。

## 7. 关键流程和生命周期

### 7.1 启动

```text
entry -> bootstrap args -> RootContext
      -> runtime/loader/trust/diagnostics/exit
      -> base + mode + user + project + explicit composition
      -> manifest/config/capability validation
      -> dependency topo sort
      -> required plugins active
      -> HostCommandRegistry command
      -> reverse dispose -> exit code
```

required entry 失败必须阻止命令启动；optional entry 失败必须可从 inventory/diagnostic 看到。

### 7.2 Prompt

```text
mode -> SessionFactory.open
     -> isolated SessionContext -> AgentContext
     -> agent-loop reads ProviderRegistry + ToolRegistry snapshot
     -> @di-code/agent one model/tool loop
     -> policy/approval/tool middleware
     -> SessionStore append before message_end completes
     -> OutputRenderer consumes typed events
     -> session dispose
```

插件不能在 handler 中自己再次调用 Provider 形成第二个循环；可扩展行为只能通过正式 registry/middleware/event。

### 7.3 unload/reload

```text
mark unloading -> remove from future resolution -> abort
-> stop new registration/events -> await in-flight work
-> reverse disposers -> remove owner contributions -> disposed
-> inventory status transition
```

迟到的 import/callback 必须检查 generation 和 Fiber phase。所有 process、HTTP stream、file handle、timer、listener 都必须覆盖成功、异常、取消、重复关闭。

## 8. 信任、安全和能力

- 项目 composition、项目 plugins、项目 MCP 默认不执行；interactive TTY 可询问 trust，non-TTY 不等待输入而是跳过并诊断。
- `--trust-project` 是显式启动选择；是否持久化由 trust plugin 决定。
- in-process plugin 不是沙箱。manifest `filesystem/network/process/ui/credentials` 只提供审计、能力服务门禁和诊断；真正不可信代码必须使用独立进程桥。
- 插件不直接读取 `process.env`、`fs`、`spawn`，而使用 `workspaceFiles`、`networkClient`、`processRunner`、`credentials` 等 capability service。
- 运行时检查 capability 和 trust；路径做 resolve/realpath/symlink boundary；spawn 使用固定 command id、结构化 args、cwd、timeout、output cap、AbortSignal；URL 只允许无凭据的绝对 HTTP(S) origin。
- 错误、日志、RPC、Session、诊断统一脱敏 `token`、`secret`、`authorization`、`api_key` 等模式，不能输出完整请求体。

## 9. Session、RPC、Provider 版本兼容

### 9.1 Session JSONL

保持 `SESSION_FORMAT_VERSION = 2`、header/message/summary、追加顺序、并发锁和恢复语义。插件私有记录使用：

```json
{ "type": "plugin", "pluginId": "example", "pluginVersion": "1.0.0", "schemaVersion": 1, "data": {} }
```

未知 plugin record 读取和重新写入时保留；每个插件记录有 migration、兼容范围和 corruption policy；插件不能直接打开 Session 文件；unload/cancel/异常要区分 committed/aborted/pending。

### 9.2 RPC

RPC v1 继续使用 `version: 1`、request `id`、event `requestId`。新 method 使用 `<pluginId>/<method>` namespace，注册时验证 params/result schema、最大输入、权限和取消。卸载期间拒绝新请求，等待或取消旧请求；shutdown 顺序必须是 response -> flush -> root dispose -> process exit。

### 9.3 版本规则

Plugin API、Composition、Session、RPC、Registry wire record 分别版本化。未知 major 拒绝，已知 major 的新增可选字段可忽略但要诊断。npm package version 不能代替协议 version。

## 10. 迁移、测试和验收

### 10.1 迁移策略

1. 先冻结现有 faux/CLI/RPC/Session/工具安全行为基线。
2. 先建 Runtime/Loader 空壳和 `faux + agent + memory session + print` minimal profile。
3. 迁移 Provider、Agent、Session 主链。
4. 逐个迁移工具、资源、CLI/TUI、RPC、MCP、orchestrator。
5. 让默认 profile 完全由 composition 提供，再删除旧 `plugins`/`extensions`。
6. 运行可插拔专项验收和发布检查。

迁移期间的 `legacy-adapter` 若确实需要，只能是私有、临时、不可发布、不可新增能力的分支工具，最后阶段必须删除。

禁止：在 `ExtensionHost` 外再包一层新 Host；`AgentSession` 同时接收新旧 host；把内建工具塞进一个大工厂；新 Loader 调用 `loadPlugins()`；为了旧测试放宽 trust/path/manifest 校验；编辑 `dist`。

### 10.2 必须覆盖的测试

Runtime：Context 继承/isolate、service visibility、Fiber phase、失败 rollback、幂等 dispose、逆序 disposer、AggregateError、async import race、EventBus abort/error、capability/trust/redaction。

Loader：namespace export shape、default 拒绝、manifest/apiVersion、composition patch、group/disabled、dependency cycle/missing、package export/path boundary、required/optional failure、inventory 和真实 fixture load。

Registry：owner disposer、duplicate/reserved/name namespace、snapshot immutability、Session isolation、tool schema/cancel/result cap、Provider/model/credential、prompt order/cache、RPC method validation。

产品组合：通过真实 CLI/bin、RPC subprocess、虚拟终端和 faux/mock server 验证 stdout/stderr、JSONL、Session 文件、ANSI、RPC event 顺序和退出码；不能只手工 mount plugin。

### 10.3 可插拔专项十项验收

1. 只加载 `runtime + faux + agent + session + print` 可以 prompt。
2. 移除所有工具后 Agent 可启动，tool snapshot 为空，tool call 得到稳定 `tool_unavailable`。
3. 只加载 `read` 时 schema 没有 write/edit/bash，且其实现未 import/初始化。
4. 用 in-memory SessionStore 替换 JSONL，Agent 行为不变且不产生文件。
5. 用 json mode 替换 print，Session/Agent factory 复用。
6. 两个 Provider 同时加载，只有选中的 factory 发请求。
7. 同一 Session plugin 在两个 isolate Context 挂载，状态完全分离。
8. tool plugin reload 100 次，贡献/listener/timer/process/file handle 不增长。
9. broken optional plugin 不影响 healthy sibling；broken required plugin 阻止命令启动。
10. 外部 npm/local fixture plugin 只依赖 SDK，真实 Loader 可加载、禁用、卸载、重载。

### 11.2 决策摘要

| 决策 | 选择 | 原因 |
| --- | --- | --- |
| 插件边界 | namespace `PluginDefinition + apply(Context, Config)` | Loader 可验证元数据、依赖和配置 |
| 生命周期 | Context/Fiber/effect/disposer | 支持 scope、取消、卸载和 owner 清理 |
| 组合 | base + mode + user + project + explicit patch | 可复现、可审计、可替换 |
| 内建功能 | 独立 plugin package/entry | 真正可 disable/replace |
| 注册 | owner-aware typed registry | 统一工具/Provider/命令/RPC 生命周期 |
| Agent loop | `@di-code/agent` 单一拥有 | 防止复制第二套循环 |
| 安全 | trust + capability + audit，明确非沙箱 | 不虚构 Node in-process 隔离 |
| 失败 | required fail-fast，optional isolated | 可操作且不拖垮整棵树 |
| 证据 | real Loader/CLI/RPC composition test | 验证用户实际入口 |
