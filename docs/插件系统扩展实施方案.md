# 插件系统扩展实施方案

## 1. 文档状态与目标

本文定义 di-code 插件系统从当前的“工具、interactive slash command 与生命周期观察器”演进为可管理运行时的实施方案。本文中的 `PluginScope`、工具中间件、动态插件命令、配置字段和 API 均为目标设计，不代表当前版本已支持。

目标是让可信插件能够在不复制 Agent Loop 的前提下贡献模型工具、提示词内容、命令、执行策略、后台资源、子 Agent 提供方和可替换的交互前端；插件停用、更新或加载失败时，贡献与资源必须完整释放。后续可在同一基础上支持由 Agent 创建的临时动态插件和 Web 前端。

本方案借鉴 DeepSeek Harness 的“注册可撤销、运行时版本化、工具执行可拦截”原则，不引入 Cordis，也不将任意 JavaScript 解释器视为安全沙箱。

## 2. 当前基础与缺口

当前插件入口、manifest、项目 trust 和全局插件管理位于 `@di-code/coding-agent`。旧插件 API 曾注册模型工具、interactive command 和 `AgentEvent`/Session 生命周期 handler；旧宿主在启动时收集这些注册，并将工具交给 `AgentSession`。目标是将可复用的插件实现整体拆到独立 workspace 包 `@di-code/plugin-runtime`，由 `coding-agent` 作为产品宿主适配，而不是继续把插件运行时私有实现嵌在 CLI 包中。

现有能力适合接入项目状态查询、团队 API 或审计观察器，但有以下结构性限制：

- 所有注册都没有 disposer。插件不能可靠地停用、更新或在失败后回收定时器、监听器和工具。
- Agent 只在构造时读取工具和 system prompt。一个插件在运行中增加工具或提示词，下一次模型请求不会自动看到变化。
- `tool_execution_start` 是工具执行已经开始后的观察事件，不能实现权限拒绝、超时、重试或规范化结果变换。
- 插件 API 没有会话状态、贡献版本、资源所有权或 UI 呈现协议，无法定义可恢复的生命周期。
- 旧扩展目录与 `.di-code/plugins/` 曾是两套发现路径和约束；长期维护会让作者无法判断应使用哪一种入口。
- `InteractiveMode` 同时拥有 AgentSession 编排、命令分发、输入、状态和 ANSI 渲染，第三方无法在不复制产品逻辑的情况下实现完整 TUI。
- 当前没有子 Agent 服务；插件若自行创建 `Agent`，会绕过父子 Session、并发、取消、工具限制和结果回传的统一管理。

`@di-code/agent` 仍必须是唯一的模型-工具循环所有者。插件、CLI、TUI、MCP 与 RPC 均不得各自发起第二个循环。

## 3. 设计原则与非目标

### 3.1 设计原则

- `@di-code/agent` 只拥有通用的模型请求快照、工具校验、执行中间件、取消和事件顺序；它不依赖插件、文件系统、TUI、Session 或 `coding-agent`。
- `@di-code/plugin-runtime` 拥有首个插件公共契约、manifest 类型、`PluginHost`、`PluginScope`、注册表、贡献快照、生命周期、诊断和动态插件协议类型；它不依赖 `coding-agent`、TUI、具体 Session 存储或 CLI。
- `@di-code/coding-agent` 拥有 `CodingAgentPluginHost` 适配器、插件发现、项目 trust、配置、Session 集成、CLI 诊断编排、`InteractiveController` 和 TUI 呈现。
- 每项贡献都由一个 `PluginScope` 持有。注册成功返回 disposer；scope 关闭时按相反顺序释放所有 disposer，并等待异步资源停稳。
- 每次模型请求使用不可变的贡献快照。模型回传的工具调用必须按发出该请求时的快照解析，避免运行中更新将调用路由到另一个实现。
- 工具执行策略进入 `@di-code/agent` 的正式管线。观察事件仍可记录行为，但不能代替拒绝或执行包裹机制。
- Agent、Session、工具执行和前端控制器属于核心运行时；ANSI TUI、Web UI、JSON 输出和 RPC 是平行的投影或驱动，不在 Agent Loop 中互相依赖。
- 一次 interactive Session 只能激活一个完整前端。完整前端独占 stdin、终端渲染、焦点、快捷键和退出流程；多个插件面板可以在同一个前端内共存。
- 子 Agent 由宿主服务创建、追踪和停止。插件只能注册 Provider、策略和投影，不能绕过服务直接创建不受管理的 Agent Loop。
- 静态本地插件仍是同进程可信代码；manifest `permissions` 是审计声明，不能宣称为 Node.js 权限边界。
- 动态插件默认关闭；若启用，运行不可信或模型生成代码必须使用子进程协议，不能用 `node:vm` 宣称隔离。

### 3.2 非目标

第一版不实现以下能力：

- 插件市场、自动安装、依赖求解或自动更新。
- 任意第三方代码的安全沙箱、细粒度 Node.js 权限或“permissions 强制执行”。
- 由插件直接读写 `Agent` 私有历史、Session JSONL 或 TUI 内部状态。
- 在首个插件 API 实现前，不实现完整替代 TUI、Web 客户端或跨进程动态插件执行。
- 动态插件跨重启自动恢复或自动写入项目源码、`package.json`、`.di-code/settings.json`。

## 4. 目标架构

```text
@di-code/ai
  Provider、消息、Tool schema、流事件
          |
@di-code/agent
  Agent Loop、请求快照、参数校验、Tool middleware、AgentEvent
          |
@di-code/plugin-runtime
  PluginApi、PluginHost、PluginScope、manifest、注册表、贡献快照
  生命周期、诊断、frontend/provider 契约、动态 JSONL RPC 类型
          |
@di-code/coding-agent
  CodingAgentPluginHost、发现/加载、trust、Session、SubagentService
  InteractiveController、CLI、内置 TUI frontend、动态进程 broker
          |
  +-- 内置工具 / MCP tools / 静态插件 / 子 Agent Provider
  +-- 可选 dynamic plugin broker（独立子进程）
          |
          +-- built-in ANSI TUI / custom TUI frontend / future Web frontend
```

依赖方向保持如下：

- `@di-code/agent` 只依赖 `@di-code/ai`，公开通用的 `AgentContextProvider` 与 `ToolExecutionMiddleware` 类型。
- `@di-code/plugin-runtime` 只通过 `@di-code/ai` 和 `@di-code/agent` 的公共入口使用消息、工具与执行中间件类型；不得导入 `coding-agent`、TUI、Provider 私有实现或 Session 文件。
- `@di-code/coding-agent` 依赖 `@di-code/plugin-runtime`，实现 `CodingAgentPluginHost`，将插件贡献适配为 Agent 所需的 context provider，并持有发现、trust、Session 和 CLI 产品策略。
- `@di-code/tui` 只作为内置 ANSI frontend 的组件库；它只接收已投影的视图模型和回调，不导入插件、Provider 或 `Agent`。
- `@di-code/orchestrator` 继续只使用公开 RPC，不访问插件宿主或动态运行时内部模块。

前端与运行时的交互统一为下列方向：

```text
AgentSession / SessionManager / CodingAgentPluginHost
  -> InteractiveController.subscribe(结构化流式事件和状态快照)
  -> 一个已选中的 InteractiveFrontend
  -> 用户输入动作
  -> InteractiveController.submit / steer / cancel / runCommand / openSession
```

前端不读取 `Agent` 私有字段、不直接写 Session JSONL，也不直接调用 Provider。它只通过 `InteractiveController` 的公开动作影响运行时。

### 4.1 Profile 组合

为接近 DSH 的多前端组合方式，`coding-agent` 增加一个由启动层解析的 runtime profile。profile 不是第二份插件 manifest，也不是可执行配置；它是已安装插件与内置能力的命名组合，决定一个进程启动哪些已批准的贡献：

```text
base
  + profile 的内置能力和已启用插件
  + 用户级 profile 覆盖
  + 已获信任的项目覆盖
  + 明确 CLI 覆盖
  = 解析后的 RuntimeProfile
```

首批内置 profile 为 `terminal`（默认内置 TUI）和 `headless`（print/json）。未来的 `web`、IDE 或自动化 profile 使用相同的核心运行时，但在独立前端或进程中消费事件协议。目标 CLI 入口是 `di-code --profile <name>`；`--ui` 是 `terminal` profile 内选择 ANSI frontend 的专用选项，不能在 `headless` profile 下使用。

一个 profile 至少声明 frontend、允许的插件 ID、工具策略和子 Agent 默认策略。它不得提供 npm 包路径、任意模块入口、Shell 命令、环境变量值或动态代码；这些能力仍由已安装插件 manifest、用户配置和独立确认流程拥有。项目 profile 只能在项目 trust 已授予时参与组合，且不能自动启用未安装的全局插件或绕过工具审批。

第一版将 profile 解析、覆盖优先级、未知 profile、重复插件和冲突 frontend 的错误行为固定为 `@di-code/coding-agent` 内部契约。profile 只引用插件 ID 和 capability，不直接依赖 `@di-code/plugin-runtime` 的模块路径；未来 CLI、Web、IDE 或嵌入 SDK 需要复用同一种 profile 文件时，再评估单独抽出 profile 包。

## 5. 第一阶段：独立插件运行时包

### 5.1 包边界与职责

新增 workspace 包 `packages/plugin-runtime/`，包名为 `@di-code/plugin-runtime`。这是插件作者和宿主集成方依赖的稳定公共入口，第一版就按独立包设计，不把实现文件从 `coding-agent` 直接暴露出去。

`@di-code/plugin-runtime` 包含：

- `apiVersion: 1` 的 manifest、能力声明和公共类型守卫。
- `PluginApi`、`PluginHost`、`PluginScope`、原子注册表、disposer 和贡献快照。
- 工具、prompt、middleware、command、Session projection、frontend、子 Agent provider 的注册契约。
- 插件生命周期状态、结构化诊断、错误分类、取消和关闭协议。
- 动态插件 Package/ActiveRun 数据模型与 JSONL RPC schema；不直接启动子进程。

`@di-code/plugin-runtime` 不包含：项目目录发现、项目 trust 持久化、CLI 参数解析、Session JSONL、内置文件工具、ANSI 渲染、Provider 凭据或子进程审批。上述能力由 `@di-code/coding-agent` 通过宿主适配器注入。这样同一个插件 runtime 可以被 CLI、未来 Web/IDE 宿主或测试 harness 复用。

拆包的目的不是把类型复制到新目录，而是让 scope、注册事务、生命周期和故障回收的实际实现只存在于 runtime 包中。宿主只能通过根入口消费稳定 API；插件 runtime 可独立测试、构建和发布，宿主可以替换而不需要重新实现插件生命周期。runtime 不反向依赖 `coding-agent`，因此不会形成 workspace 循环依赖。

### 5.2 旧实现的保留与退役

考虑到当前项目尚未发布且目标是 Vibe Coding，本方案允许在实现期间暂时保留旧插件代码，但只作为迁移参考和回归基线，不作为新运行时的兼容层：

- 阶段 0 先冻结旧插件 API、旧宿主、旧 loader 和扩展目录发现逻辑，不再给它们新增功能。
- 新的 `@di-code/plugin-runtime` 与 `CodingAgentPluginHost` 使用独立目录、独立入口和独立测试；新 loader 不读取旧扩展目录，也不把旧类型适配到 `apiVersion: 1`。
- 迁移期间可保留旧源码、fixture 和测试，便于对照现有行为；它们不得成为新包的生产依赖，也不得出现在新包的公共导出中。
- 当新 runtime、宿主适配、内置插件、CLI、Session 和前端回归测试全部通过后，在收尾阶段一次性删除旧 loader、旧类型、旧扩展目录、旧 fixture、旧测试和旧文档示例。
- 删除旧代码前执行一次全仓库引用扫描；删除后测试必须证明旧目录和旧入口不会被发现。若发现仍有真实消费者，应先完成迁移，不通过隐式兼容解决。

因此，旧代码可以后续删除，但最终发布的代码树和运行时只保留新插件实现；这不是旧版本兼容策略。

### 5.3 `PluginScope` 与原子注册

`@di-code/plugin-runtime` 的 `PluginHost` 为每个已加载插件创建一个 scope。插件 factory 只能通过 scope 绑定的 API 注册贡献；factory 完成前，runtime 在暂存区验证命名空间、冲突、schema 和宿主声明的保留命令名。验证成功后一次性提交，失败时不泄露部分注册。

```ts
export interface Disposable {
	dispose(): void | Promise<void>;
}

export interface PluginScope {
	readonly pluginId: string;
	readonly state: "loading" | "active" | "stopping" | "stopped" | "failed";
	dispose(): Promise<void>;
}

export interface PluginApi {
	registerTool<T extends TSchema>(tool: PluginTool<T>): Disposable;
	registerCommand(command: PluginCommand): Disposable;
	registerPromptSection(section: PluginPromptSection): Disposable;
	useToolMiddleware(middleware: ToolExecutionMiddleware): Disposable;
	registerInteractiveFrontend(frontend: PluginInteractiveFrontend): Disposable;
	registerSubagentProvider(provider: SubagentProvider): Disposable;
	on<E extends PluginEventType>(event: E, handler: PluginEventHandler<E>): Disposable;
	registerSessionProjection(projection: PluginSessionProjection): Disposable;
	effect(start: () => void | Disposable | Promise<void | Disposable>): Disposable;
}

export type PluginFactory = (api: PluginApi) => void | Promise<void>;
```

`dispose()` 必须幂等。若两个 disposer 失败，宿主继续释放剩余资源，最终以一个聚合诊断报告失败项；不得因一个插件的清理失败而跳过其他插件或阻塞 Session 关闭。新 scope 激活前，旧 scope 仍保持工作；新 scope 完整提交后才切换，旧 scope 随后停止。这保证更新不会留下“工具已换、事件仍旧”的混合状态。

新运行时统一入口为 `.di-code/plugins/<plugin-id>/` 和 package `diCode.plugins`。实现期间旧扩展目录和旧插件 API 可以暂时留在源码树中，但新 loader 不读取它们；仓库内现有插件、fixture、测试和文档示例在迁移阶段改为首个插件 API，阶段 7 再删除旧实现。旧实现从始至终没有兼容入口。

### 5.4 Agent 请求快照

`Agent` 目前在构造时复制 system prompt 与工具列表。第一阶段改为在每一个 Provider 请求开始前调用只读 context provider：

```ts
export interface AgentRequestContext {
	readonly systemPrompt?: string;
	readonly tools: readonly AgentTool[];
}

export interface AgentContextProvider {
	resolve(signal?: AbortSignal): Promise<AgentRequestContext> | AgentRequestContext;
}
```

一次请求得到的 `AgentRequestContext` 是不可变快照。该响应内的每个 tool call 都使用同一快照中的工具定义和执行器；工具结果进入下一轮后，Agent 再取得新快照。这样插件可在工具调用后注册新工具或提示词，且这些贡献只影响下一次模型请求。

`AgentContextProvider` 由 `@di-code/agent` 拥有，`CodingAgentPluginHost` 将 `@di-code/plugin-runtime` 的贡献注册表适配为该接口。没有插件时，现有静态工具数组适配为固定快照，原有 SDK 行为保持不变。

### 5.5 提示词贡献

插件不接触完整会话历史，只能提交具名 section：

```ts
export interface PluginPromptSection {
	readonly id: string;
	readonly order: number;
	readonly render: (context: PluginPromptContext) => string | Promise<string | undefined>;
}
```

宿主按 `(order, pluginId, id)` 排序，跳过 `undefined`，并将结果与内置 system prompt 组合。`PluginPromptContext` 只包含 `cwd`、模式、项目 trust、当前模型和取消信号；不暴露 API key、完整 Session、其他插件私有配置或 TUI 对象。

prompt section 失败不应产生半个 Provider 请求。解析快照时，宿主将该次请求终止为明确的插件错误，写入诊断，并保留上一轮 Session 历史；是否继续禁用该插件由后续故障策略决定。

### 5.6 工具中间件

`@di-code/agent` 在完成工具定位和参数 schema 校验后执行中间件。每个中间件获得已校验参数、工具调用 ID、名称和 `AbortSignal`，并以 `next()` 包裹后续执行：

```ts
export interface ToolExecution<TParameters = unknown> {
	readonly toolCallId: string;
	readonly tool: AgentTool;
	readonly parameters: TParameters;
	readonly signal?: AbortSignal;
}

export type ToolExecutor = (execution: ToolExecution) => Promise<AgentToolResult>;
export type ToolExecutionMiddleware = (execution: ToolExecution, next: ToolExecutor) => Promise<AgentToolResult>;
```

执行顺序固定为：

```text
模型 tool call
  -> 从该请求快照定位工具
  -> schema 校验
  -> tool_execution_start
  -> middleware[注册顺序]
  -> 工具 execute
  -> middleware 反向返回
  -> 标准化 ToolResultMessage
  -> tool_execution_end
  -> 下一轮请求
```

中间件可以拒绝调用、附加计时、替换 `AbortSignal`、重试可判定的失败或规范化结果。拒绝和中间件异常必须转换为现有标准工具错误结果，仍发出 `tool_execution_end`；取消始终优先于成功结果。中间件不得直接调用 Provider 或递归调用 `Agent.prompt()`。

权限确认、超时、重试和审计是此 API 的预期消费者。仅观察行为使用既有 `on()`，不应占用中间件链。

### 5.7 命令与后台资源

`registerCommand()` 继续只在 interactive 模式可用，但返回 disposer。命令 handler 应收到一个受限 `PluginCommandContext`，包括原始参数、`cwd`、Session ID、取消信号和一个受宿主管理的 `notify()`；`notify()` 只产生用户可见状态消息，不能调用模型或改写终端布局。

插件需要后台资源时必须在 scope 中注册，例如 `api.effect(async () => disposer)`。宿主在 Session 关闭、插件禁用、更新、加载失败和进程退出路径等待 disposer。插件可以注册有限的前端面板数据和工具详情 renderer，但不能直接写 ANSI 控制序列、操纵 `TUI` 实例、取得输入焦点或重排内置布局。

## 6. 可替换交互前端

### 6.1 目标与所有权

完整自定义 TUI 不属于普通面板插件。它是一个 `InteractiveFrontend`：用户显式选择后，替代默认 ANSI TUI 成为一个 interactive Session 唯一的终端所有者。内置 TUI 保留为默认实现，`@di-code/tui` 不需要重写；需要拆分的是 `InteractiveMode` 中的运行时编排和展示逻辑。

```text
di-code --interactive --ui builtin
di-code --interactive --ui acme-terminal
```

`--ui` 是目标 CLI 选项。`builtin` 选择现有 TUI 的适配实现；其他值必须是一个已加载、声明了 `interactiveFrontend` 的可信插件 ID。`print`、`json` 和 RPC 模式不启动 `InteractiveFrontend`，所以不受该选项影响。

### 6.2 `InteractiveController` 公共接口

`@di-code/coding-agent` 定义并拥有面向产品的 `InteractiveController`。`@di-code/plugin-runtime` 只定义 frontend 注册、生命周期和 capability 的宿主无关契约；coding-agent 将 Controller 和终端能力注入已选 frontend。Controller 将 AgentSession、SessionManager、内置命令、插件命令、取消、前端可见诊断与 Session 选择投影为前端无关协议：

```ts
export interface InteractiveFrontend {
	start(controller: InteractiveController, terminal: TerminalFrontendHost): Promise<void>;
	dispose(): Promise<void>;
}

export interface InteractiveController {
	readonly state: InteractiveViewState;
	subscribe(listener: (event: InteractiveViewEvent) => void): Disposable;
	submit(input: InteractiveInput): Promise<void>;
	steer(input: InteractiveInput): void;
	cancel(): void;
	runCommand(name: string, args: string): Promise<void>;
	selectModel(modelId: string): void;
	openSession(sessionId: string): Promise<void>;
	createSession(): Promise<void>;
	requestCompaction(): Promise<void>;
}
```

`InteractiveViewEvent` 必须覆盖当前 interactive 模式已经呈现的业务事实：输入与 streaming 状态、`message_start`、`message_update`、`message_end`、工具开始/结束、使用量、队列、Session 树、可用模型、插件/MCP 诊断和退出状态。流式文本、思考和工具调用增量以结构化 event 交付；前端自行缓存其临时呈现状态，`message_end` 与 Session 记录才是可恢复的最终内容。

Controller 的动作必须定义错误、取消和并发行为。处于 streaming 时，`submit` 遵循现有 steering 规则或明确拒绝；前端不得自行调用 `Agent.prompt()` 绕过该规则。Controller 负责串行化 Session 切换和模型切换，保证前端不必理解 Agent 的私有锁。

`TerminalFrontendHost` 是宿主创建的独占终端门面，提供输入事件、尺寸变化、原始模式、写入和恢复能力。只有选中的 frontend 收到该对象；它不得改用 `process.stdin`、`process.stdout` 或创建第二个终端读取器。宿主负责在 `start()` 拒绝、异常和 `dispose()` 后恢复终端模式。

### 6.3 内置与自定义 TUI 的共存

启动时，宿主完成插件加载后解析 `--ui`：

1. 未指定时使用 `builtin`。
2. 指定的插件不存在、未启用、未获项目 trust、未注册 frontend 或在启动阶段失败时，启动失败并给出 `plugin_diagnostic`；不得静默回退到内置 TUI。
3. frontend 成功 `start()` 后独占 stdin、原始终端模式、ANSI 写入、焦点与退出处理。
4. frontend 停止、崩溃或用户退出时，宿主先取消活跃 prompt，再等待 Controller、插件 scope、MCP 和 Session 清理完成。

一个插件前端可以用任意 ANSI 布局重做界面，但必须实现与内置 TUI 相同的核心交互能力：多行输入、流式输出、工具状态、取消、重试、slash command、模型选择、Session 创建/切换、上下文压缩、错误与诊断展示。高级的主题、图片粘贴、树导航和设置页可通过接口版本化为可选 capability；前端必须在未声明 capability 时有明确降级行为。

### 6.4 前端插件 API 与普通 UI 贡献

首个插件 API 的 manifest 增加可选 frontend 声明，factory 通过 `registerInteractiveFrontend()` 提供实现。该注册方法、`PluginInteractiveFrontend` 和 `InteractiveFrontend` 生命周期类型由 `@di-code/plugin-runtime` 导出；`InteractiveController`、`TerminalFrontendHost` 和实际 CLI 绑定由 `@di-code/coding-agent` 提供。普通插件仍只能提供受限面板和工具详情 renderer，由当前选中的 frontend 选择如何显示；普通贡献绝不能替换输入所有权。

```ts
export interface PluginInteractiveFrontend {
	readonly id: string;
	readonly displayName: string;
	readonly capabilities: readonly InteractiveFrontendCapability[];
	create(): InteractiveFrontend | Promise<InteractiveFrontend>;
}
```

前端实现除 `TerminalFrontendHost` 外不接收 Node 进程、其他插件私有状态、Provider、SessionStorage 或 Agent 内部 API。它的所有业务动作和事件订阅都来自 Controller；停止时必须释放其终端和事件资源。

### 6.5 未来 Web 前端

Web 前端不复用同进程 Node 插件来操作 DOM。未来新增 Web 应用时，它作为另一种 `InteractiveFrontend` consumer，使用版本化事件协议或现有 RPC 的扩展流投影连接 Host。Web 侧插件采用声明式 slot/视图模型和受限 Host RPC，不能获得 Node 模块或用户凭据。

Web、内置 TUI、第三方 TUI、headless 和 RPC 是平行 profile/entry，不是彼此抢占同一个界面的多个插件。先完成 Controller 和自定义 TUI，再单独设计 Web transport、认证、页面生命周期和浏览器插件授权。

## 7. 子 Agent 扩展

### 7.1 服务边界

子 Agent 由 `@di-code/coding-agent` 中的 `SubagentService` 统一拥有，第一阶段不再为子 Agent 另建 workspace 包。`@di-code/plugin-runtime` 导出 `SubagentProvider`、请求约束和结果类型；coding-agent 的服务负责创建子 `AgentSession`、记录父子关系、限制深度与并发、传播取消、收集受限结果并负责关闭。它必须复用 `@di-code/agent` 的唯一工具循环，插件不得自行维护第二套 loop。

```text
父 Agent 的 subagent 工具
  -> SubagentService.start(request)
  -> 已选择的 SubagentProvider
  -> 子 AgentSession / 外部受控进程
  -> 状态与最终报告
  -> 父 Agent 下一轮的工具结果或 steering context
```

### 7.2 Provider 与策略注册

插件可注册 `SubagentProvider`，而不是注册任意 Agent 实例。首个内置 provider 是进程内新 Session；后续可增加 `di-code` 子进程、RPC、ACP 或其他外部 Agent provider。每次启动都必须解析一个宿主拥有的 request/spec，明确父 Session、工作目录、模型、工具可见集、插件可见集、最大深度、超时和是否允许继续对话。

```ts
export interface SubagentProvider {
	readonly id: string;
	start(request: SubagentStartRequest, signal?: AbortSignal): Promise<SubagentRun>;
}

export interface SubagentRun {
	readonly id: string;
	readonly status: "running" | "completed" | "failed" | "cancelled";
	wait(signal?: AbortSignal): Promise<SubagentResult>;
	sendMessage(input: InteractiveInput, signal?: AbortSignal): Promise<void>;
	cancel(): Promise<void>;
}
```

插件还可注册工具白名单、提示词 section、审批策略、结果摘要器和 TUI view model。所有子 Agent 的文件操作、命令、网络调用和进一步委派仍通过子 Agent 自己的工具策略执行；父插件不能因为是创建方而绕过这些限制。

### 7.3 生命周期与持久化

`SubagentService` 将启动、状态变化、最终报告、取消和故障投影为父 Session 的版本化记录。父 Agent 可通过模型工具 `subagent`、`subagent_list`、`send_message`、`wait` 和 `interrupt` 控制由当前授权范围允许的子任务；具体命名在实现前固定并测试。结果进入父 Agent 上下文前必须有大小上限、凭据脱敏和明确的关联 ID。

插件 scope 停止时，宿主先取消其拥有的 runs，等待 provider 释放进程/监听器，再卸载工具和 UI 贡献。子 Agent 崩溃、超时、取消与普通工具错误必须可区分，并且不得让父 Session 永久停在等待状态。

## 8. Session、诊断与版本

### 8.1 Session 持久化

普通插件的运行时注册不写入 Session。需要恢复的插件状态必须显式注册 `PluginSessionProjection`，并使用由插件 ID 限定的版本化 record：

```ts
export interface PluginSessionRecord {
	readonly type: "plugin_state";
	readonly pluginId: string;
	readonly version: 1;
	readonly data: JsonValue;
}
```

宿主只持久化经 JSON 序列化检查的数据，不持久化函数、源码、环境变量、Authorization header 或未脱敏异常。恢复时不存在对应插件、插件禁用、版本不兼容或数据无效都必须产生诊断，不能静默丢弃记录。引入此 record 前必须同步更新 Session 存储、恢复、压缩、RPC 投影、测试和格式文档。

### 8.2 诊断

插件诊断继续使用 `plugin_diagnostic`，但增加稳定的 `stage`：`discover`、`manifest`、`load`、`register`、`prompt`、`middleware`、`handler`、`dispose`、`session_restore`。诊断包含插件 ID、来源、严重性和已脱敏消息；不得包含密钥、完整请求体、任意工具参数或源码。

interactive 模式显示插件状态与最近失败摘要；print/json 模式继续写 stderr JSONL。插件的失败必须与 Agent/Provider/Session 错误分开，便于 RPC 和 TUI 消费方分类处理。

### 8.3 API 版本

重构后的首个插件格式直接使用 manifest `apiVersion: 1`，factory 使用由 `@di-code/plugin-runtime` 导出的 `PluginApi`。`@di-code/plugin-runtime` 的 loader/manifest 校验只接受这个新契约；旧插件 API、旧宿主和扩展目录都不保留运行时适配器或发现逻辑。

本仓库尚未发布插件兼容承诺，因此实现期间分阶段替换现有示例、fixture、测试和插件指南，验收完成后删除旧实现；不新增运行时迁移层或弃用周期。这里的 `apiVersion: 1` 指重构后的首个公开契约；当前代码中的旧实现不是需要兼容的版本。

## 9. 动态插件

动态插件只在第一阶段稳定后实现。它用于让用户批准 Agent 在当前会话中定义并试运行临时代码，不替代正常的项目插件开发与发布流程。

### 9.1 生命周期与模型工具

动态 Package/ActiveRun 注册表和协议状态由 `@di-code/plugin-runtime` 拥有，默认仅存在内存；子进程启动、用户确认、项目 trust 和 CLI 展示由 `@di-code/coding-agent` 的 dynamic plugin broker 负责：

```text
DynamicPlugin（Session 所有者）
  -> Package 1 / Package 2 ...（不可变代码、manifest 摘要、诊断）
  -> ActiveRun（一个动态插件子进程与一个 PluginScope）
```

建议提供下列模型工具，所有工具均按定义会话校验所有权：

- `plugin_inspect`：只读列出可用动态 API、Plugin、Package、Run 状态和诊断。
- `plugin_define`：预检源码、运行时版本、声明能力和资源限制，创建不可变 Package；不执行代码。
- `plugin_run`：经用户批准后启动 Package，成功后才设为当前版本。
- `plugin_update`：启动新 Package；新 run 成功后切换，失败时旧 run 保持活跃。
- `plugin_stop`：终止当前动态插件子进程并释放 scope，保留 Package 以便重新运行或回滚。
- `plugin_remove`：先停止，再删除内存中的 Plugin、Package 和授权记录。

动态 Package 不能自动写入 `.di-code/plugins/`、安装 npm 包、修改工作区配置或在重启后恢复。若实验应成为正式能力，Agent 必须用普通文件工具生成、测试和安装一个静态插件，由用户审查后再启用。

### 9.2 进程隔离与能力协议

动态代码运行在独立 Node 子进程中，通过版本化 JSONL RPC 与宿主通信。该进程隔离生命周期、崩溃和通信协议，但自身不是安全沙箱；在没有额外操作系统级限制时，动态代码仍可能访问 Node.js 和用户权限可见的资源。因此动态插件必须保持默认关闭、经过逐次用户确认，并视同本地代码执行。

第一版动态协议只允许：

- 注册带 TypeBox/JSON Schema 的 namespaced 模型工具。
- 注册 prompt section、工具中间件和事件观察器。
- 接收受限的 `PluginContext` 与取消信号。
- 发送结构化日志和主动释放资源通知。

文件、网络、Shell 和进程能力不作为 RPC 协议的隐式成员。需要这些效果时，动态工具必须调用宿主已公开、具备独立校验与审批语义的能力；第一版应默认不提供此桥接。动态代码结果、跨进程参数和日志都是不可信输入，必须按 JSON schema、大小限制、超时与取消信号验证。若未来需要执行不完全可信代码，必须单独引入并验证操作系统级沙箱，不能以子进程或 `node:vm` 命名替代安全保证。

动态插件子进程崩溃、协议错误、超时或重复关闭必须使 `ActiveRun` 进入 `failed`/`stopped`，释放该 scope，并记录脱敏诊断。运行动态插件不授予比当前用户选择的工作区、内置工具和审批策略更高的权限。

### 9.3 用户确认与 CLI

动态能力默认关闭，显式启动开关建议为 `--allow-dynamic-plugins`。interactive 模式在每次 `plugin_run`/`plugin_update` 前显示 Plugin ID、Package 版本、声明的能力、代码摘要和影响范围，并要求一次明确确认。print/json/RPC 模式默认拒绝动态运行；只有未来增加独立的非交互授权配置并完成安全设计后才能开放。

动态代码的确认不能与项目 trust 混用：项目 trust 决定是否 import 项目中的静态 Node.js 插件，动态确认决定是否执行当前会话提交的临时代码，两者存储、过期和审计语义不同。

### 10.1 Vibe Coding 上下文拆分

实现采用“一个架构切片对应一个新上下文”的方式。上下文由用户手动切换，Codex 不能也不应假设自己可以创建或切换上下文。新上下文共享工作区文件，但不依赖上一个上下文的隐式记忆；用户启动新上下文时应提供上一阶段交接摘要，并让 AI 读取 `AGENTS.md`、`README.md`、本方案、`git status` 和相关 diff。一个上下文只负责一个切片，遇到失败或未完成事项时留在当前切片继续处理，不能带着半成品进入下一切片。

推荐按以下 9 个上下文批次执行；批次内部仍按上表阶段顺序逐项完成：

### 10.2 AI 完整实现硬性规则

以下规则是阶段门禁，AI 必须执行，不能以“后续再补”代替：

1. **先读方案再改代码。** 开始前必须明确当前阶段、责任包、公共接口、依赖方向、验收测试和不属于本阶段的内容。
2. **实现完整闭环。** 每项功能必须同时覆盖正常路径、参数/边界错误、取消、超时、异常、重复调用、资源释放和用户可见诊断；只实现 happy path 不算完成。
3. **禁止伪完成。** 不得留下空函数、`TODO` 代替逻辑、固定假数据、永远成功的 stub、吞异常、静默回退、跳过测试或只导出类型而没有运行时实现。
4. **禁止隐式缩 scope。** 如果原方案中的功能无法在当前上下文完成，必须报告 `partial` 或 `blocked`，列出剩余文件、行为和测试；不得自行删掉需求后宣称完成。
5. **先测试再切阶段。** 每个公共契约都要有行为测试；跨包、Session、RPC、TUI、子 Agent 和插件生命周期必须覆盖两端或所有投影。测试失败时继续当前阶段，不得进入下一阶段。
6. **证据化验收。** 完成摘要必须逐项列出“方案要求 -> 实现位置 -> 测试 -> 实际命令输出”；仅描述“已完成”没有证据不算通过。
7. **真实集成优先。** 新包必须被 `coding-agent` 的真实入口使用；新 TUI 必须消费真实流式事件；子 Agent 必须走宿主服务；动态插件必须走真实 RPC 生命周期。fixture 只能补充，不能替代集成。
8. **不破坏边界。** 不从其他包的 `src`/`dist` 私有路径导入，不让插件或 frontend 创建第二套 Agent Loop，不让普通插件直接写 ANSI、Session JSONL 或 Provider。

### 10.3 阶段完成门禁

只有以下条件全部满足，当前上下文才可以向用户报告“本阶段可切换”；实际切换由用户手动完成：

- 当前阶段的功能矩阵全部有实现，不存在未解释的 TODO、stub 或临时绕过。
- 相关 workspace 测试通过，并新增了本阶段的成功、失败、取消、并发和清理测试。
- `npm run check` 通过；涉及公共导出、CLI、RPC、子进程或包 metadata 时，相关 workspace build 和根目录 `npm run build` 通过。
- 真实入口回归通过：无插件、内置插件、新插件、Faux Provider 和对应 CLI/TUI/JSON/RPC 模式均有验证。
- `git diff --check` 通过，未覆盖用户已有改动，公共 API、README、CLI help 和本方案已同步。
- 旧实现状态明确：迁移未完成时旧代码只冻结且不被新 loader 使用；阶段 7 之后旧引用已全部删除。
- 生成下一阶段交接摘要，并明确用户切换后下一上下文只能处理的一个 bounded action。

如果任一门禁不满足，阶段状态只能是 `partial` 或 `blocked`；AI 必须留在当前阶段继续处理或明确报告阻塞，不得声称可以切换，也不得开始下一阶段。

## 11. 测试与验收

### 11.1 静态插件、前端与子 Agent 阶段

- 请求快照测试：插件在工具执行期间添加工具或 prompt section 时，当前 response 不变，下一次 Provider 请求出现新贡献。
- 工具中间件测试：允许、拒绝、链式顺序、参数校验失败、异常、超时、取消、结果变换及 `tool_execution_start/end` 顺序。
- scope 测试：注册冲突不提交任何贡献；多 disposer 逆序释放；重复 dispose 幂等；一个 disposer 失败不阻断其余清理。
- 更新测试：新插件失败时旧版本继续可用；新版本完整提交后旧 scope 才卸载；同名工具与命令没有空窗或双重注册。
- Session 测试：插件状态 append、恢复、未知插件、版本不兼容、损坏 JSON 和压缩后的投影行为。
- 模式测试：interactive 命令与 TUI 状态、print/json `plugin_diagnostic`、RPC Session 关闭均保持确定性。
- 回归测试：无插件、新插件 API、MCP tools、Faux Provider 与原有 CLI 流程行为不变；旧入口和旧扩展目录不再发现，旧实现的加载路径被删除。
- 迁移退役测试：新 runtime 验收前旧源码仍可作为对照 fixture；退役阶段删除后，全仓库无旧插件 API、旧宿主、旧 loader 和扩展目录的生产引用或测试引用。
- frontend 测试：内置 frontend 与完整自定义 frontend 接收相同的流式事件；只有选中的 frontend 读取 stdin 和写 ANSI；启动失败不静默回退；退出、取消、窄终端和非 TTY 的清理与降级行为确定。
- controller 测试：提交、steering、取消、命令、模型切换、Session 切换、重试和压缩的输入条件、并发拒绝与事件顺序固定；前端不需要访问 `Agent` 私有状态。
- 子 Agent 测试：最大深度和并发、工具白名单、父子取消、结果大小限制、provider 崩溃、重复关闭、插件卸载和父 Session 关闭均不遗留活动 run。
- profile 测试：基础 profile、用户/项目/CLI 覆盖顺序、未知 profile、重复插件、冲突 frontend、未获 trust 的项目覆盖和 `headless` profile 下误用 `--ui` 都有确定错误。
- package boundary 测试：`@di-code/plugin-runtime` 可独立 typecheck/build/test；其源码不导入 `coding-agent`、TUI 私有模块或 Session 文件；coding-agent 只通过 runtime 根入口和宿主适配器接入。

### 11.2 动态与 Web 阶段

- `define` 不执行代码；语法、schema、大小和能力声明错误被明确拒绝。
- `run` 只在确认后启动；取消、拒绝、子进程超时、崩溃、协议畸形和重复 stop 不残留工具、监听器或子进程。
- 新 Package 启动失败不会中断旧 Package；回滚和 remove 释放所有资源。
- Session/RPC 不保存源码或密钥；重启后动态 Plugin 不存在且产生明确状态说明。
- 动态 Package 的 RPC 只能访问声明的宿主能力；测试不得将子进程隔离误写为 Node.js 权限限制。
- Web transport 测试：断线、重连、过期 event、未授权 frontend、取消和页面销毁不会改变 Host 的 Agent/Session 所有权；浏览器插件只能操作声明的 slot 与 RPC 能力。

每个阶段至少运行对应 workspace 测试与 `npm run check`。新增或修改 `@di-code/plugin-runtime` 根入口、CLI、RPC 或动态插件子进程入口时运行对应 workspace build 和根目录 `npm run build`；所有文档或源码变更完成后运行 `git diff --check`。
