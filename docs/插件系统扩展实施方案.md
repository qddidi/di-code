# 插件系统扩展实施方案

## 1. 文档状态与目标

本文定义 di-code 插件系统从当前的“工具、interactive slash command 与生命周期观察器”演进为可管理运行时的实施方案。本文中的 `PluginScope`、工具中间件、动态插件命令、配置字段和 API 均为目标设计，不代表当前版本已支持。

目标是让可信插件能够在不复制 Agent Loop 的前提下贡献模型工具、提示词内容、命令、执行策略、后台资源和有限的 TUI 呈现；插件停用、更新或加载失败时，贡献与资源必须完整释放。后续可在同一基础上支持由 Agent 创建的临时动态插件。

本方案借鉴 DeepSeek Harness 的“注册可撤销、运行时版本化、工具执行可拦截”原则，不引入 Cordis，也不将任意 JavaScript 解释器视为安全沙箱。

## 2. 当前基础与缺口

当前插件入口、manifest、项目 trust 和全局插件管理位于 `@di-code/coding-agent`。`ExtensionAPI` 可以注册模型工具、interactive command 和 `AgentEvent`/Session 生命周期 handler；`ExtensionHost` 在启动时收集这些注册，并将工具交给 `AgentSession`。

现有能力适合接入项目状态查询、团队 API 或审计观察器，但有以下结构性限制：

- 所有注册都没有 disposer。插件不能可靠地停用、更新或在失败后回收定时器、监听器和工具。
- Agent 只在构造时读取工具和 system prompt。一个插件在运行中增加工具或提示词，下一次模型请求不会自动看到变化。
- `tool_execution_start` 是工具执行已经开始后的观察事件，不能实现权限拒绝、超时、重试或规范化结果变换。
- 插件 API 没有会话状态、贡献版本、资源所有权或 UI 呈现协议，无法定义可恢复的生命周期。
- `.di-code/extensions/` 与 `.di-code/plugins/` 是两套发现路径和约束；长期维护会让作者无法判断应使用哪一种入口。

`@di-code/agent` 仍必须是唯一的模型-工具循环所有者。插件、CLI、TUI、MCP 与 RPC 均不得各自发起第二个循环。

## 3. 设计原则与非目标

### 3.1 设计原则

- `@di-code/agent` 只拥有通用的模型请求快照、工具校验、执行中间件、取消和事件顺序；它不依赖插件、文件系统、TUI、Session 或 `coding-agent`。
- `@di-code/coding-agent` 拥有插件加载、manifest、trust、插件作用域、Session 集成、CLI 诊断与 TUI 呈现。
- 每项贡献都由一个 `PluginScope` 持有。注册成功返回 disposer；scope 关闭时按相反顺序释放所有 disposer，并等待异步资源停稳。
- 每次模型请求使用不可变的贡献快照。模型回传的工具调用必须按发出该请求时的快照解析，避免运行中更新将调用路由到另一个实现。
- 工具执行策略进入 `@di-code/agent` 的正式管线。观察事件仍可记录行为，但不能代替拒绝或执行包裹机制。
- 静态本地插件仍是同进程可信代码；manifest `permissions` 是审计声明，不能宣称为 Node.js 权限边界。
- 动态插件默认关闭；若启用，运行不可信或模型生成代码必须使用子进程协议，不能用 `node:vm` 宣称隔离。

### 3.2 非目标

第一版不实现以下能力：

- 插件市场、自动安装、依赖求解或自动更新。
- 任意第三方代码的安全沙箱、细粒度 Node.js 权限或“permissions 强制执行”。
- 由插件直接读写 `Agent` 私有历史、Session JSONL 或 TUI 内部状态。
- 浏览器 Client 插件、Web UI 注入或跨进程执行模型-工具循环。
- 动态插件跨重启自动恢复或自动写入项目源码、`package.json`、`.di-code/settings.json`。

## 4. 目标架构

```text
@di-code/ai
  Provider、消息、Tool schema、流事件
          |
@di-code/agent
  Agent Loop、请求快照、参数校验、Tool middleware、AgentEvent
          |
@di-code/coding-agent
  PluginHost、PluginScope、静态加载、trust、Session、CLI、TUI
          |
  +-- 内置工具 / MCP tools / 静态插件
  +-- 可选 DynamicPluginRuntime（独立 Worker）
```

依赖方向保持如下：

- `@di-code/agent` 只依赖 `@di-code/ai`，公开通用的 `AgentContextProvider` 与 `ToolExecutionMiddleware` 类型。
- `@di-code/coding-agent` 将 `PluginHost` 适配为 Agent 所需的 context provider，并持有所有产品策略。
- `@di-code/tui` 只接收已投影的插件视图模型和回调，不导入插件、Provider 或 `Agent`。
- `@di-code/orchestrator` 继续只使用公开 RPC，不访问插件宿主或动态运行时内部模块。

## 5. 第一阶段：稳定的静态插件运行时

### 5.1 `PluginScope` 与原子注册

`PluginHost` 为每个已加载插件创建一个 scope。插件 factory 只能通过 scope 绑定的 API 注册贡献；factory 完成前，宿主在暂存区验证命名空间、冲突、schema 和保留命令名。验证成功后一次性提交，失败时不泄露部分注册。

```ts
export interface Disposable {
	dispose(): void | Promise<void>;
}

export interface PluginScope {
	readonly pluginId: string;
	readonly state: "loading" | "active" | "stopping" | "stopped" | "failed";
	dispose(): Promise<void>;
}

export interface PluginApi {
	registerTool<T extends TSchema>(tool: PluginTool<T>): Disposable;
	registerCommand(command: PluginCommand): Disposable;
	registerPromptSection(section: PluginPromptSection): Disposable;
	useToolMiddleware(middleware: ToolExecutionMiddleware): Disposable;
	on<E extends PluginEventType>(event: E, handler: PluginEventHandler<E>): Disposable;
	registerSessionProjection(projection: PluginSessionProjection): Disposable;
	effect(start: () => void | Disposable | Promise<void | Disposable>): Disposable;
}

export type PluginFactory = (api: PluginApi) => void | Promise<void>;
```

`dispose()` 必须幂等。若两个 disposer 失败，宿主继续释放剩余资源，最终以一个聚合诊断报告失败项；不得因一个插件的清理失败而跳过其他插件或阻塞 Session 关闭。新 scope 激活前，旧 scope 仍保持工作；新 scope 完整提交后才切换，旧 scope 随后停止。这保证更新不会留下“工具已换、事件仍旧”的混合状态。

第一阶段统一入口为 `.di-code/plugins/<plugin-id>/` 和 package `diCode.plugins`。`.di-code/extensions/` 仅作为 API v1 的过渡发现路径，迁移完成后删除；新增能力不得再落入该目录。

### 5.2 Agent 请求快照

`Agent` 目前在构造时复制 system prompt 与工具列表。第一阶段改为在每一个 Provider 请求开始前调用只读 context provider：

```ts
export interface AgentRequestContext {
	readonly systemPrompt?: string;
	readonly tools: readonly AgentTool[];
}

export interface AgentContextProvider {
	resolve(signal?: AbortSignal): Promise<AgentRequestContext> | AgentRequestContext;
}
```

一次请求得到的 `AgentRequestContext` 是不可变快照。该响应内的每个 tool call 都使用同一快照中的工具定义和执行器；工具结果进入下一轮后，Agent 再取得新快照。这样插件可在工具调用后注册新工具或提示词，且这些贡献只影响下一次模型请求。

`AgentContextProvider` 由 `@di-code/agent` 拥有，`PluginHost` 只是 `@di-code/coding-agent` 中的一个实现来源。没有插件时，现有静态工具数组适配为固定快照，原有 SDK 行为保持不变。

### 5.3 提示词贡献

插件不接触完整会话历史，只能提交具名 section：

```ts
export interface PluginPromptSection {
	readonly id: string;
	readonly order: number;
	readonly render: (context: PluginPromptContext) => string | Promise<string | undefined>;
}
```

宿主按 `(order, pluginId, id)` 排序，跳过 `undefined`，并将结果与内置 system prompt 组合。`PluginPromptContext` 只包含 `cwd`、模式、项目 trust、当前模型和取消信号；不暴露 API key、完整 Session、其他插件私有配置或 TUI 对象。

prompt section 失败不应产生半个 Provider 请求。解析快照时，宿主将该次请求终止为明确的插件错误，写入诊断，并保留上一轮 Session 历史；是否继续禁用该插件由后续故障策略决定。

### 5.4 工具中间件

`@di-code/agent` 在完成工具定位和参数 schema 校验后执行中间件。每个中间件获得已校验参数、工具调用 ID、名称和 `AbortSignal`，并以 `next()` 包裹后续执行：

```ts
export interface ToolExecution<TParameters = unknown> {
	readonly toolCallId: string;
	readonly tool: AgentTool;
	readonly parameters: TParameters;
	readonly signal?: AbortSignal;
}

export type ToolExecutor = (execution: ToolExecution) => Promise<AgentToolResult>;
export type ToolExecutionMiddleware = (execution: ToolExecution, next: ToolExecutor) => Promise<AgentToolResult>;
```

执行顺序固定为：

```text
模型 tool call
  -> 从该请求快照定位工具
  -> schema 校验
  -> tool_execution_start
  -> middleware[注册顺序]
  -> 工具 execute
  -> middleware 反向返回
  -> 标准化 ToolResultMessage
  -> tool_execution_end
  -> 下一轮请求
```

中间件可以拒绝调用、附加计时、替换 `AbortSignal`、重试可判定的失败或规范化结果。拒绝和中间件异常必须转换为现有标准工具错误结果，仍发出 `tool_execution_end`；取消始终优先于成功结果。中间件不得直接调用 Provider 或递归调用 `Agent.prompt()`。

权限确认、超时、重试和审计是此 API 的预期消费者。仅观察行为使用既有 `on()`，不应占用中间件链。

### 5.5 命令、后台资源与 TUI

`registerCommand()` 继续只在 interactive 模式可用，但返回 disposer。命令 handler 应收到一个受限 `PluginCommandContext`，包括原始参数、`cwd`、Session ID、取消信号和一个受宿主管理的 `notify()`；`notify()` 只产生用户可见状态消息，不能调用模型或改写终端布局。

插件需要后台资源时必须在 scope 中注册，例如 `api.effect(async () => disposer)`。宿主在 Session 关闭、插件禁用、更新、加载失败和进程退出路径等待 disposer。第一阶段 TUI 只提供两种只读贡献：工具详情 renderer 与状态面板 view model；插件不能插入任意组件、取得输入焦点或直接写 ANSI 控制序列。

## 6. Session、诊断与版本

### 6.1 Session 持久化

普通插件的运行时注册不写入 Session。需要恢复的插件状态必须显式注册 `PluginSessionProjection`，并使用由插件 ID 限定的版本化 record：

```ts
export interface PluginSessionRecord {
	readonly type: "plugin_state";
	readonly pluginId: string;
	readonly version: 1;
	readonly data: JsonValue;
}
```

宿主只持久化经 JSON 序列化检查的数据，不持久化函数、源码、环境变量、Authorization header 或未脱敏异常。恢复时不存在对应插件、插件禁用、版本不兼容或数据无效都必须产生诊断，不能静默丢弃记录。引入此 record 前必须同步更新 Session 存储、恢复、压缩、RPC 投影、测试和格式文档。

### 6.2 诊断

插件诊断继续使用 `plugin_diagnostic`，但增加稳定的 `stage`：`discover`、`manifest`、`load`、`register`、`prompt`、`middleware`、`handler`、`dispose`、`session_restore`。诊断包含插件 ID、来源、严重性和已脱敏消息；不得包含密钥、完整请求体、任意工具参数或源码。

interactive 模式显示插件状态与最近失败摘要；print/json 模式继续写 stderr JSONL。插件的失败必须与 Agent/Provider/Session 错误分开，便于 RPC 和 TUI 消费方分类处理。

### 6.3 API 版本迁移

新增 manifest `apiVersion: 2`，其 factory 使用 `PluginApi`。`apiVersion: 1` 的 `ExtensionAPI` 通过单独适配器载入到一个 `PluginScope`，保留当前工具、命令和观察事件语义；它不能使用中间件、prompt section、Session projection 或 TUI 贡献。

适配层在发布说明和插件指南中标注废弃目标版本。移除 v1 前必须提供迁移说明、迁移 fixture，并在一个明确的破坏性版本中删除 `.di-code/extensions/` 发现路径和 v1 类型导出；不得长期维护两套独立运行时。

## 7. 第二阶段：动态插件

动态插件只在第一阶段稳定后实现。它用于让用户批准 Agent 在当前会话中定义并试运行临时代码，不替代正常的项目插件开发与发布流程。

### 7.1 生命周期与模型工具

动态注册表由 `@di-code/coding-agent` 拥有，默认仅存在内存：

```text
DynamicPlugin（Session 所有者）
  -> Package v1 / v2 ...（不可变代码、manifest 摘要、诊断）
  -> ActiveRun（一个 Worker 与一个 PluginScope）
```

建议提供下列模型工具，所有工具均按定义会话校验所有权：

- `plugin_inspect`：只读列出可用动态 API、Plugin、Package、Run 状态和诊断。
- `plugin_define`：预检源码、运行时版本、声明能力和资源限制，创建不可变 Package；不执行代码。
- `plugin_run`：经用户批准后启动 Package，成功后才设为当前版本。
- `plugin_update`：启动新 Package；新 run 成功后切换，失败时旧 run 保持活跃。
- `plugin_stop`：终止当前 Worker 并释放 scope，保留 Package 以便重新运行或回滚。
- `plugin_remove`：先停止，再删除内存中的 Plugin、Package 和授权记录。

动态 Package 不能自动写入 `.di-code/plugins/`、安装 npm 包、修改工作区配置或在重启后恢复。若实验应成为正式能力，Agent 必须用普通文件工具生成、测试和安装一个静态插件，由用户审查后再启用。

### 7.2 进程隔离与能力协议

动态代码运行在独立 Node Worker 或子进程中，通过版本化 JSONL RPC 与宿主通信。Worker 没有 `process`、文件系统、网络、Shell、环境变量或宿主模块的直接访问能力；它只能调用宿主明确暴露的能力。

第一版动态协议只允许：

- 注册带 TypeBox/JSON Schema 的 namespaced 模型工具。
- 注册 prompt section、工具中间件和事件观察器。
- 接收受限的 `PluginContext` 与取消信号。
- 发送结构化日志和主动释放资源通知。

文件、网络、Shell 和进程能力不作为 Worker API 的隐式成员。需要这些效果时，动态工具必须调用宿主已公开、具备独立校验与审批语义的能力；第一版应默认不提供此桥接。动态代码结果、跨进程参数和日志都是不可信输入，必须按 JSON schema、大小限制、超时与取消信号验证。

Worker 崩溃、协议错误、超时或重复关闭必须使 `ActiveRun` 进入 `failed`/`stopped`，释放该 scope，并记录脱敏诊断。运行动态插件不授予比当前用户选择的工作区、内置工具和审批策略更高的权限。

### 7.3 用户确认与 CLI

动态能力默认关闭，显式启动开关建议为 `--allow-dynamic-plugins`。interactive 模式在每次 `plugin_run`/`plugin_update` 前显示 Plugin ID、Package 版本、声明的能力、代码摘要和影响范围，并要求一次明确确认。print/json/RPC 模式默认拒绝动态运行；只有未来增加独立的非交互授权配置并完成安全设计后才能开放。

动态代码的确认不能与项目 trust 混用：项目 trust 决定是否 import 项目中的静态 Node.js 插件，动态确认决定是否执行当前会话提交的临时代码，两者存储、过期和审计语义不同。

## 8. 实施顺序与代码落点

| 阶段 | 责任位置 | 工作内容 |
| --- | --- | --- |
| 0 | `packages/coding-agent/src/plugins/`、`extensions/` | 盘点 v1 生产消费者，固定当前插件加载、错误和事件测试。 |
| 1 | `packages/agent/src/types.ts`、`agent-loop.ts`、`agent.ts` | 增加 `AgentContextProvider`、请求快照与工具中间件，保持现有静态工具构造方式可用。 |
| 2 | `packages/coding-agent/src/plugins/` | 实现 `PluginScope`、事务性注册、统一 loader、贡献注册表和诊断。 |
| 3 | `packages/coding-agent/src/core/session.ts`、`core/system-prompt.ts`、`modes/interactive.ts` | 将 PluginHost 接入 AgentSession、prompt 组合、命令、Session/TUI 投影与关闭路径。 |
| 4 | `packages/coding-agent/src/plugins/manifest.ts`、文档 | 发布 API v2，保留受限 v1 适配器与迁移说明。 |
| 5 | `packages/coding-agent/src/dynamic-plugins/` | 增加内存注册表、Worker RPC、审批 UI、动态工具和故障回收。 |

阶段 1 至 3 是一个可交付单元：完成后，静态插件已经可以安全地贡献策略与资源，动态能力不应阻塞这部分发布。阶段 5 必须在单独设计评审后实施，因为它新增代码执行与用户授权面。

## 9. 测试与验收

### 9.1 第一阶段

- 请求快照测试：插件在工具执行期间添加工具或 prompt section 时，当前 response 不变，下一次 Provider 请求出现新贡献。
- 工具中间件测试：允许、拒绝、链式顺序、参数校验失败、异常、超时、取消、结果变换及 `tool_execution_start/end` 顺序。
- scope 测试：注册冲突不提交任何贡献；多 disposer 逆序释放；重复 dispose 幂等；一个 disposer 失败不阻断其余清理。
- 更新测试：新插件失败时旧版本继续可用；新版本完整提交后旧 scope 才卸载；同名工具与命令没有空窗或双重注册。
- Session 测试：插件状态 append、恢复、未知插件、版本不兼容、损坏 JSON 和压缩后的投影行为。
- 模式测试：interactive 命令与 TUI 状态、print/json `plugin_diagnostic`、RPC Session 关闭均保持确定性。
- 回归测试：无插件、v1 插件、MCP tools、Faux Provider 与原有 CLI 流程行为不变。

### 9.2 动态阶段

- `define` 不执行代码；语法、schema、大小和能力声明错误被明确拒绝。
- `run` 只在确认后启动；取消、拒绝、Worker 超时、崩溃、协议畸形和重复 stop 不残留工具、监听器或子进程。
- 新 Package 启动失败不会中断旧 Package；回滚和 remove 释放所有资源。
- Session/RPC 不保存源码或密钥；重启后动态 Plugin 不存在且产生明确状态说明。
- Worker 无法直接读取环境变量、执行命令、加载任意宿主模块或访问不在协议内的文件与网络能力。

每个阶段至少运行对应 workspace 测试与 `npm run check`。涉及根入口、CLI、RPC 或 Worker 入口时运行 `npm run build`；所有文档或源码变更完成后运行 `git diff --check`。

阶段 1 至 4 实现时，更新插件指南以说明 API v2、贡献生命周期、执行顺序、取消、Session state 和 v1 迁移；更新 `packages/agent/README.md` 说明 context provider 与中间件公共接口；更新 `packages/coding-agent/README.md` 和根 `README.md` 的用户可见范围。动态阶段实现时，另行更新 CLI help、信任/确认说明、RPC 文档、Session 格式说明与安全限制。
