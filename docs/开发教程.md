# 开发教程

本文面向修改 di-code 源码、编写集成程序和开发 namespace plugin 的贡献者。根目录 [README.md](../README.md) 负责用户安装和 CLI 行为；包级 README 负责公开 API；本文负责源码导航、跨包约束、扩展流程和验证方法。

## 1. 开发环境

项目使用 ESM、TypeScript strict、NodeNext、`verbatimModuleSyntax`、`erasableSyntaxOnly` 和 npm workspaces。要求 Node.js `>=22.19.0` 与 npm：

```powershell
npm install --ignore-scripts
npm run check
npm test
npm run build
```

首次安装建议使用 `--ignore-scripts`。日常修改先运行受影响 workspace 的测试和根 `npm run check`；只有改动公共类型、Provider、Agent loop、RPC、Web 构建入口或发布脚本时才需要扩大到完整 build/release 检查。

## 2. Workspace 全景

仓库包含 12 个 workspace：11 个公开包和 1 个私有 Web 前端包。依赖应保持单向：AI 契约不依赖产品层，Agent 只消费 AI，coding-agent 组装产品运行时，orchestrator 只通过 RPC 通信，TUI 和 Web 不实现 Agent loop。

| --- | --- | --- | --- | --- |

### 包之间如何协作

```text
@di-code/ai
    |
@di-code/agent
    |
@di-code/builtins ---- @di-code/skills
    |  \              @di-code/tui
    |   \             @di-code/mcp
@di-code/coding-agent ---- @di-code/web
    |
@di-code/orchestrator --(公开 RPC)-- di-code-rpc 子进程

@di-code/plugin-runtime <- @di-code/plugin-loader <- @di-code/plugin-sdk（第三方入口）
```

图示表达职责层次，不代表可以跨层导入内部文件。跨包只能使用 `@di-code/*` 根入口或 package.json 明确声明的 public subpath；禁止从另一个包的 `src`、`dist` 或测试 fixture 导入。

### 公共 API 与组合入口

外部应用通常只需要以下根入口：`@di-code/ai`（Provider/Model/消息类型）、`@di-code/agent`（Agent loop）、`@di-code/tui`（ANSI 组件）、`@di-code/mcp`（MCP client）、`@di-code/orchestrator`（RPC supervisor）和 `@di-code/plugin-sdk`（插件开发）。`@di-code/coding-agent` 还提供 `./rpc`、`./ui-host`、`./webui`、`./rpc-client-sdk` 等明确声明的 subpath；使用前先查看该包 `package.json.exports`。

`@di-code/builtins` 不是一个必须整体加载的“大工厂”。它把 Provider（`provider-openai`、`provider-anthropic`、`provider-deepseek`、`provider-kimi`、`provider-zhipu`、`provider-faux`）、工具（`tool-read`、`tool-write`、`tool-edit`、`tool-bash`、`tool-glob`、`tool-grep` 等）、Session、mode、TUI 和 RPC 拆成 namespace entries。Composition 应选择所需 subpath，以保持依赖和生命周期可审查；只有需要公共类型或完整默认 profile 时才使用根入口。

`@di-code/plugin-runtime` 与 `@di-code/plugin-loader` 适合宿主和运行时开发，第三方插件应通过 `@di-code/plugin-sdk` 导入。`@di-code/web` 是随 coding-agent 构建的私有 React workspace，不发布 npm 包；Web 行为的服务端入口在 `coding-agent/src/webui.ts`，前端入口在 `web/src/main.tsx`。

## 4. 新增或修改 Provider

1. 在 `packages/ai/src/providers/` 选择最接近的 API 适配器，复用统一 `Provider`、`Model`、`Message` 和 `StreamEvent` 类型。
2. 在 `src/api/` 中把厂商响应映射为文本、thinking、tool call、tool result、usage 和规范化错误；不得把厂商私有字段泄漏到 Agent 或插件公共类型。
3. 为模型声明 `input`、`reasoning`、`contextWindow`、`maxTokens` 等能力。模型生成目录应通过现有脚本更新，不直接编辑 `dist` 或生成文件。
4. 在 `packages/builtins` 增加独立 provider namespace entry，并接入 provider/model registry；凭据缺失的可选 Provider 应保留脱敏诊断，而不是让整个 composition 静默失败。
5. 增加无网络单元测试；真实 smoke 测试必须由环境变量显式启用，缺少 key 时跳过。同步根 README、配置示例和包 README。

## 5. 新增工具、命令或 mode

### 工具

工具使用 TypeBox schema 和 `execute(toolCallId, parameters, signal)`。Agent 执行前会再次校验模型参数；工具实现仍需把路径、命令、URL、超时、输出大小和取消当作不可信边界。

- 文件工具先经过 allowed-root canonicalization，拒绝越界路径和逃逸 symlink。
- `bash` 使用结构化 executable/args、明确 cwd、超时、输出截断和 AbortSignal；它不是操作系统级 sandbox。
- 通过 `ToolRegistry` 注册，并在 Session 创建时形成 immutable tool snapshot；会话启动后禁用工具不会被动态补回。

### 命令和 mode

命令通过 `CommandRegistry` 注册，帮助文本从 registry inventory 生成。mode 通过 `ModeRegistry`/`RendererRegistry` 接入 `print`、`json`、`interactive` 或 `rpc` composition，不要在 CLI、TUI、Web 中复制 Agent loop。RPC `run_command` 只能执行 `list_commands` 返回的已注册名称。

## 6. Plugin runtime、Loader 与 SDK

`plugin-runtime` 定义 Context/Fiber 生命周期、typed service key、事件和 contribution owner；`plugin-loader` 负责 manifest、Composition、trust 和受管安装；`plugin-sdk` 是第三方插件应依赖的唯一稳定入口。插件开发细节见 [插件使用指南](插件使用指南.md)，源码改动时尤其要测试：

- entry 的 namespace export、API version、package exports 和路径/symlink 边界；
- Composition 的层顺序、`$ENV_VAR` 替换、依赖拓扑、patch、required/optional 失败；
- Fiber disposer 的逆序、重复 dispose、取消、in-flight setup 和错误聚合；
- contribution 的 owner 清理、重复/保留名称和 namespace 冲突；
- Web manifest 的 slot、capability、bundle SHA-256/CSP 和未知 slot 兼容。

权限声明和 capability view 用于加载与审计，不是 Node.js 沙箱。插件不得记录 token、Authorization header 或完整请求体。

## 7. Session、Skills、MCP 和 RPC 的持久化/协议规则

Session JSONL 是 durable data：记录只追加，保留 version、父节点、锁、分支和损坏诊断；未知或不兼容版本不能静默丢弃。修改字段时同步存储、恢复、压缩、SessionHost、RPC 和测试。

Skill 是有大小和 frontmatter 校验的提示词文本，不授予权限，也不自动执行。项目 Skill 和 MCP 配置受 Workspace trust 影响；trust 控制 import eligibility，不替代来源审查。

RPC 每条记录保留 `version: 1`，请求以 `id` 关联，事件以 `requestId` 和可选 sequence 关联。新增方法必须同步 protocol validator、dispatcher、server、client、SDK、并发/取消测试和文档。事件恢复必须处理 `resume_events`、有界重放缓冲和 `snapshot_required`。

MCP manager 由创建它的宿主拥有并关闭；显式重连不等于任意请求自动重试。stdio 不经过 shell 拼接，HTTP headers 只引用环境变量；错误需要分类、脱敏和截断。

## 8. Web 和 TUI 开发

TUI 组件实现 `render(width): string[]` 与 `invalidate()`，状态变化后调用 `requestRender()`；使用 `visibleWidth` 等工具处理中文和宽字符。测试应使用虚拟终端覆盖固定宽高、光标、Overlay 截断、输入法/粘贴、取消和窄屏布局。TUI 不得依赖 Provider 或 coding-agent。

Web 前端通过 `/api/boot`、窄 RPC 和 SSE snapshot 获取数据；浏览器不能接触 API key、绝对路径、transport token 或插件 Node 代码。Web slot 只渲染宿主白名单的 `componentKey` 和 JSON-like data。修改 `packages/web` 时运行该 workspace 的 Vitest 和 Vite build，并检查断线重连、`snapshot_required`、错误态、Settings 保存和移动端抽屉。

## 9. Orchestrator 开发

Orchestrator 只能导入 `@di-code/coding-agent/rpc` 的公开协议/SDK。 `RpcSupervisor.start()` 必须等待 `get_state` 握手；子进程 crash 要将 pending request 以 `PROCESS_EXIT` 拒绝并保留有界 stderr，不自动重启或重放可能产生副作用的请求。 `stop()` 先 SIGTERM，超时后 SIGKILL，且可重复调用。对应测试在 `packages/orchestrator/test/`。

## 10. 测试、构建和发布

按变更范围选择最小充分检查：

```powershell
# 单个包
npm test --workspace @di-code/ai

# 类型、格式和全部构建
npm run check
npm run build

# 全部 workspace 测试
npm test

# 发布候选（会构建 tarball 并验证安装，不上传）
npm run release:dry-run
```

CLI、RPC、插件、Session、Provider 和 Web 行为应优先用 `DI_CODE_PROVIDER=faux` 做离线验证；真实网络测试必须显式使用环境变量并在缺少 key 时跳过。提交前执行：

```powershell
git diff --check
npm run check
npm test
git status --short
```

版本使用 `npm run version:prepare -- <major.minor.patch>` 同步 workspace 与 lockfile。不要手工编辑 `dist/`，不要提交 `.env`、`.di-code/`、Session、coverage、临时文件或真实密钥。

## 11. 常见问题定位

| 现象 | 检查方向 |
| --- | --- |
| Provider 未配置 | `DI_CODE_PROVIDER`、settings 合并顺序、对应 key 环境变量和模型 ID |
| Plugin skipped/failed | `--trace-plugins`、manifest exports、trust、依赖和 required 标记 |
| 工具找不到或权限错误 | Composition 是否加载、ToolRegistry snapshot、workspace/capability/approval |
| Session 无法打开 | JSONL version、损坏记录、锁文件、工作区 hash 和 `--session` 路径 |
| WebUI 断线 | token/Origin、`Last-Event-ID`、resume token、sequence 和 `snapshot_required` |
| TUI 花屏或溢出 | 虚拟终端尺寸、ANSI 清理、`visibleWidth`、Overlay maxHeight 和 invalidate |
| RPC 请求挂起 | request ID 是否唯一、dispatcher operation table、AbortSignal、子进程 stderr |

排错输出必须经过脱敏；不要为了复现问题打印完整 settings、环境变量、请求体或授权 header.

## 12. 开发者编码规范

以下规则适用于所有 workspace；根目录 `AGENTS.md` 是冲突时的最终依据。

### TypeScript 与模块

- 所有包使用 ESM，`package.json` 必须保持 `"type": "module"`；相对 TypeScript import 保留 `.ts` 扩展名，不引入 CommonJS-only export。
- 遵循 `strict: true`、NodeNext、`verbatimModuleSyntax` 和 `erasableSyntaxOnly`。优先使用精确 union、类型守卫和显式返回类型，禁止用 `any` 绕过边界；确需使用时必须说明原因。
- 代码格式遵循 Biome：tab 缩进、120 列和推荐 lint 规则。格式化时不要混入无关行为修改。
- 跨包只从 `@di-code/*` 根入口或已声明的 public subpath 导入；不得依赖另一个包的 `src`、`dist` 或测试文件。

### API、事件与生命周期

- 公共导出、非显然的错误/并发/生命周期行为写简短 JSDoc，说明参数、返回值、拒绝条件、取消、所有权和副作用。
- 消息、工具、事件和 RPC 使用明确 discriminant；封闭 union 使用 `assertNever`，可扩展 union 保留明确的未知值 fallback。
- 谁创建资源谁负责释放。`AbortSignal`、文件句柄、子进程、监听器、MCP 连接和临时文件必须覆盖成功、失败、取消和重复关闭路径。
- Agent loop 只由 `@di-code/agent`/SessionHost 拥有；Provider、CLI、插件、TUI、Web 和 orchestrator 不实现第二套循环。
- TUI 只处理 presentation props/events，Web 只通过窄 RPC 和脱敏 snapshot 访问产品状态；不得把产品逻辑下沉到展示包。

### 安全与输入校验

路径、URL、命令片段、模型 JSON、项目文件、Skill、MCP Server 和插件输入全部视为不可信。实现文件工具时检查 canonical root、symlink 逃逸、编码和大小；实现进程工具时使用结构化参数、固定 cwd、超时、输出上限和取消；实现网络和插件能力时脱敏 token、secret、authorization、api_key 等内容。不要为了让测试通过而放宽边界、吞掉异常或静默兼容损坏数据。

### 测试与文档

修复 bug 时先添加能复现用户可观察行为的测试，再修改实现。测试应覆盖边界、错误、取消、并发和资源清理，而不是复制内部实现。网络 smoke 测试必须由环境变量显式启用，缺少 key 时跳过，并优先使用 Faux Provider 做离线验证。

凡是修改 CLI 选项、Provider 配置、插件 API、Session 格式、RPC 字段、工具限制或用户可见输出，都要在同一变更中更新所属 README/指南、CLI help、JSDoc 和测试。纯内部重构可以不新增文档，但应在变更说明中明确。

## 13. Git 与提交规范

### 变更组织

- 一个提交只包含一个逻辑主题；不要把重构、功能、格式化和无关文档混在一起。
- 提交前检查 `git diff --stat` 和 `git diff --check`，确认没有意外文件、密钥、`.env`、`.di-code/`、`node_modules/`、`dist/`、coverage 或临时输出。
- 不覆盖或重置其他开发者已有的未提交改动；发生冲突时基于当前工作区继续修改，并在提交说明中指出假设或限制。
- 生成文件由脚本维护：模型目录、`dist/` 和 `package-lock.json` 不手工编辑；依赖变化通过 npm 更新 lockfile。

### 提交信息

提交信息使用以下前缀，并在冒号后写清意图：

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `feat:` | 新增用户或 API 能力 | `feat: add Kimi provider entry` |
| `fix:` | 修复行为或安全问题 | `fix: reject escaping workspace symlink` |
| `refactor:` | 不改变行为的结构调整 | `refactor: split session host services` |
| `test:` | 只增加或调整测试 | `test: cover RPC resume sequence` |
| `docs:` | 只修改文档或注释 | `docs: expand WebUI setup guide` |
| `chore:` | 构建、版本、依赖和发布维护 | `chore: release 0.1.2` |

标题应简短、使用祈使语气并说明结果；公共协议或持久化格式变更应在正文记录兼容性、迁移和安全影响。不要在提交、日志或变更说明中写入真实 API key、Authorization header 或完整请求体。

### 提交前门禁

根据变更范围运行最小充分检查：

```powershell
git diff --check
git status --short
npm run check
npm test
```

单包行为修改至少运行 `npm test --workspace @di-code/<package>`；公共类型、Provider、Agent、RPC 或构建入口修改还要运行 `npm run build`；发布相关修改还要运行 `npm run release:dry-run`。提交前确认文档链接、命令、环境变量、包名和 JSON 字段与源码一致。
