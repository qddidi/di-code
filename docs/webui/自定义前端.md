# 从零开发自定义 WebUI 前端

如果你不想使用 di-code 内置的 React 页面，而是要用 Vue、Svelte、Solid、原生 HTML，甚至桌面壳重新做一套界面，可以直接使用 `di-code-webui` 的 HTTP/SSE 接口。

有公开 API：协议版本为 `v1`，请求、响应和事件的类型定义在 `@di-code/coding-agent/rpc` 以及仓库的 [`packages/coding-agent/src/rpc/protocol.ts`](https://github.com/qddidi/di-code/blob/master/packages/coding-agent/src/rpc/protocol.ts) 中。浏览器前端使用 HTTP/SSE envelope；Node.js 宿主也可以直接使用 `@di-code/coding-agent/rpc` 的 `RpcClient`。

这条路径的结构是：

```text
你的前端  --POST /rpc------>  di-code-webui  --> Agent / Session
你的前端  <--GET /events----  di-code-webui  <-- 流式事件
你的前端  --POST /attachments-> di-code-webui <-- 图片附件
```

前端只负责界面和状态投影；Provider、Agent loop、工具审批、Session 持久化仍由 di-code 服务端负责。

## 1. 启动后端

自定义前端应连接 `di-code-webui`，而不是连接 `di-code web` 的内置页面：

```powershell
$env:DI_CODE_PROVIDER = "faux"
$env:DI_CODE_WEBUI_PORT = "8787"
$env:DI_CODE_WEBUI_TOKEN = "replace-with-a-random-token-of-at-least-32-characters"
di-code-webui
```

开发完成后，把 `DI_CODE_PROVIDER` 换成真实 Provider，并按 [CLI 与配置](../用户指南/CLI与配置.md) 设置模型和 API key。

示例中的地址是 `http://127.0.0.1:8787`；这是因为上面的命令显式设置了 `DI_CODE_WEBUI_PORT=8787`。未设置该变量时，服务使用端口 `0`，由系统分配随机可用端口，并在 stderr 输出实际地址。默认只接受 loopback 请求；如果前端运行在另一个本地端口，例如 `http://127.0.0.1:3000`，服务会允许这个同机 HTTP Origin。远程绑定必须同时设置 `DI_CODE_WEBUI_ALLOW_REMOTE=1`，并在反向代理、防火墙或自定义 `WebUiServer` 配置中限制可信 Origin 和网络访问范围。`di-code-webui` 命令行入口没有单独的 Origin 白名单环境变量；跨域部署建议使用同源反向代理，或在 Node.js 中构造 `WebUiServer({ origins: [...] })`。

远程启动时，`DI_CODE_WEBUI_HOST` 应填写客户端实际访问的主机名或 IP；服务端会校验请求的 `Host`，因此不要把 `0.0.0.0` 当作浏览器访问地址。

所有需要认证的请求都带以下任一 header：

```http
Authorization: Bearer <DI_CODE_WEBUI_TOKEN>
```

或：

```http
X-Di-Code-Token: <DI_CODE_WEBUI_TOKEN>
```

不要把 token 放在 URL、前端打包产物、日志或 Session 中。生产环境通常应让自己的后端保存 token，再由后端代理浏览器请求；如果必须让浏览器直连，只在可信的本机环境使用。

## 2. 三个 HTTP 入口

### `POST /rpc`

发送一个版本化 RPC 请求：

```json
{
  "version": 1,
  "kind": "request",
  "id": "req-001",
  "method": "get_state",
  "params": {}
}
```

成功响应：

```json
{
  "version": 1,
  "kind": "response",
  "id": "req-001",
  "ok": true,
  "result": {
    "method": "get_state",
    "state": {
      "sessionId": "session-id",
      "modelId": "gpt-4o",
      "isStreaming": false,
      "messageCount": 0,
      "sequence": 0
    }
  }
}
```

失败响应的 `ok` 为 `false`，`error.code` 是稳定错误码，例如 `INVALID_PARAMS`、`BUSY`、`NOT_FOUND`、`CANCELLED` 或 `UNAUTHORIZED`。前端应显示可读错误，但不要把完整请求体或凭据显示给用户。

### `GET /events`

这是流式 SSE 连接。连接成功后首先收到：

```text
event: ready
data: {"resumeToken":"..."}
```

后续事件的 `data` 是 RPC event envelope：

```json
{
  "version": 1,
  "kind": "event",
  "requestId": "prompt-001",
  "sessionId": "session-id",
  "sequence": 12,
  "event": {
    "type": "message_update",
    "event": { "type": "text_delta", "contentIndex": 0, "delta": "你好" }
  }
}
```

事件可能包括 `message_start`、`message_update`、`message_end`、`tool_execution_start`、`tool_execution_end`、`usage_update`、`operation_update`、`session_changed` 和 `snapshot_required`。前端应按 `sequence` 去重并保持最后一个序号。

支持图片输出的 Provider 会在 `message_update` 中发送原子图片事件，并在 `message_end`/`prompt` 结果的 assistant message `content` 中保留同一图片：

```json
{
  "type": "message_update",
  "event": {
    "type": "image",
    "contentIndex": 0,
    "image": { "type": "image", "mimeType": "image/png", "data": "<base64>" }
  }
}
```

前端应在校验 MIME 和大小后，将图片作为助手消息的一部分渲染；图片不是用户附件，也不能把服务端本地路径直接暴露给浏览器。

MCP 工具返回的图片会出现在 `tool_execution_end` 的 `result.content` 中；内置 WebUI 会在对应工具卡片中渲染它。工具生成的文件路径仍由 MCP 服务自身决定，di-code 不会把工具输出自动搬到全局 `.di-code` 目录。

原生 `EventSource` 不能自定义 `Authorization` header，因此带 token 的浏览器前端应使用 `fetch()` 读取 `response.body`，或者让自己的后端代理 SSE。仓库中的 [`examples/webui-client.ts`](../../examples/webui-client.ts) 展示了基于 `fetch` 的读取方式。

### `POST /attachments`

上传图片时发送 JSON：

```json
{
  "name": "screenshot.png",
  "contentType": "image/png",
  "data": "<base64，不含 data:image/png;base64, 前缀>"
}
```

响应中的 `result.attachment.id` 是不透明句柄。之后在 `prompt` 或 `steer` 的 `attachmentIds` 中传入它。支持 PNG、JPEG、WebP 和 GIF；单张最多 5 MiB，每次请求最多 4 张。附件被消费、过期或服务关闭后会删除，前端不能自行拼接服务端文件路径。

## 3. 推荐的前端启动顺序

一个最小可用前端通常按这个顺序工作：

1. 建立 `/events` SSE 连接，保存 `resumeToken`。
2. 调用 `get_capabilities`，协商需要的扩展事件。
3. 调用 `list_sessions`；没有会话时调用 `new_session`。
4. 调用 `get_transcript`、`get_runtime` 和 `get_models` 初始化页面。
5. 用户发送消息时调用 `prompt`，同时监听 SSE 中与该 `requestId` 关联的事件。
6. 断线重连时带上 `X-Di-Code-Resume-Token` 和 `Last-Event-ID`。
7. 如果收到 `snapshot_required`，重新读取 state、transcript、tree 和 usage，不要猜测丢失的事件，也不要自动重放 prompt。

## 4. 一个可直接改造的 JavaScript 客户端

下面的代码只依赖浏览器原生 `fetch`，可放进任意前端框架的 service/store 中：

```js
const baseUrl = "http://127.0.0.1:8787";
const token = "replace-with-your-token";

let clientId;
let resumeToken;
let lastSequence = 0;

function headers(extra = {}) {
	return {
		Authorization: `Bearer ${token}`,
		...(clientId ? { "X-Di-Code-Client-Id": clientId } : {}),
		...extra,
	};
}

async function rpc(method, params = {}, id = crypto.randomUUID()) {
	const response = await fetch(`${baseUrl}/rpc`, {
		method: "POST",
		headers: headers({ "Content-Type": "application/json" }),
		body: JSON.stringify({ version: 1, kind: "request", id, method, params }),
	});
	const returnedClientId = response.headers.get("x-di-code-client-id");
	if (returnedClientId) clientId = returnedClientId;
	const value = await response.json();
	if (!response.ok || value.ok !== true) {
		const error = value.error ?? { code: String(response.status), message: response.statusText };
		throw new Error(`${error.code}: ${error.message}`);
	}
	return value.result;
}

async function connectEvents(onEvent) {
	const eventResponse = await fetch(`${baseUrl}/events`, {
		headers: headers({
			...(resumeToken ? { "X-Di-Code-Resume-Token": resumeToken } : {}),
			...(lastSequence > 0 ? { "Last-Event-ID": String(lastSequence) } : {}),
		}),
	});
	if (!eventResponse.ok || !eventResponse.body) throw new Error("SSE connection failed");

	const reader = eventResponse.body.getReader();
	const decoder = new TextDecoder();
	let buffer = "";
	for (;;) {
		const chunk = await reader.read();
		if (chunk.done) break;
		buffer += decoder.decode(chunk.value, { stream: true });
		const records = buffer.split("\n\n");
		buffer = records.pop() ?? "";
		for (const record of records) {
			if (record.startsWith(": keepalive")) continue;
			const dataLine = record.split("\n").find((line) => line.startsWith("data: "));
			if (!dataLine) continue;
			const message = JSON.parse(dataLine.slice(6));
			if (message.resumeToken) resumeToken = message.resumeToken;
			if (Number.isSafeInteger(message.sequence)) lastSequence = Math.max(lastSequence, message.sequence);
			if (message.event) onEvent(message);
		}
	}
}

const eventsTask = connectEvents((message) => {
	// 将 message.event 投影到你的 store，例如更新流式文本或工具状态。
	console.log(message.requestId, message.event.type, message.event);
});

await rpc("get_capabilities", {
	events: ["sequence", "operation_update", "snapshot_required", "session_changed"],
});

const sessions = await rpc("list_sessions");
const session = sessions.sessions[0] ?? (await rpc("new_session")).session;
await rpc("open_session", { sessionId: session.id });
const prompt = await rpc("prompt", { sessionId: session.id, message: "请简要介绍当前项目。" }, "prompt-001");
console.log(prompt.message);

void eventsTask.catch((error) => console.error("SSE closed", error));
```

实际项目中，`connectEvents` 应在独立任务中持续运行，而不是阻塞按钮事件；`prompt` 返回的是最终 assistant message，流式增量来自 SSE。同一 Session 的另一个 `prompt` 会返回 `BUSY`，可以用 SSE `operation_update` 中该运行的 `runId` 调用 `cancel`：

```js
await rpc("cancel", { sessionId: session.id, runId: "<operation_update.runId>", requestId: "prompt-001" });
```

取消只停止当前请求，不删除已写入的 Session 记录。失败或取消后，可以用 `retry` 指定目标 request：

```js
await rpc("retry", { sessionId: session.id, targetRequestId: "prompt-001" });
```

## 5. 常用 RPC 方法

所有方法都使用同一个 `{ version, kind, id, method, params }` envelope。下面列出自定义前端最常用的一组；服务端返回的 `result.method` 与请求方法相同。

| 方法 | 关键参数 | 用途 |
| --- | --- | --- |
| `get_capabilities` | `{ events?: string[] }` | 协商方法和扩展事件 |
| `get_state` | `{}` | 当前 Session、模型、流式状态 |
| `list_sessions` | `{}` | 获取当前工作区的 Session 列表 |
| `new_session` | `{}` | 创建并切换到新 Session |
| `open_session` | `{ sessionId }` | 切换当前 Session |
| `get_transcript` | `{ pageToken?, pageSize?, maxBytes? }` | 分页读取消息 |
| `get_tree` | `{}` | 读取历史分支树 |
| `prompt` | `{ sessionId, message, attachmentIds? }` | 发送一轮对话 |
| `steer` | `{ sessionId, runId, message, attachmentIds? }` | 给正在运行的 Agent 追加引导 |
| `cancel` | `{ sessionId, runId, requestId }` | 取消 queued/running operation |
| `retry` | `{ sessionId, targetRequestId }` | 重试失败或取消的 prompt |
| `get_operation` | `{ sessionId, runId, requestId }` | 查询 operation 状态 |
| `get_models` | `{}` | 获取当前可用模型 |
| `get_runtime` | `{}` | 获取当前 Provider、模型和 thinking level |
| `get_usage` | `{}` | 获取 token、费用和上下文使用量 |
| `get_settings` | `{}` | 获取脱敏设置快照 |
| `list_providers` | `{}` | 获取 Provider 和模型目录 |
| `list_web_contributions` | `{}` | 获取插件声明的 Web contribution |
| `list_commands` | `{}` | 获取可执行 command/skill 清单 |
| `run_command` | `{ name, args? }` | 执行清单中的命令 |

设置、MCP、插件和项目 trust 也有对应 RPC，例如 `set_runtime`、`login`、`configure_custom_provider`、`configure_mcp_server`、`set_plugin_enabled` 和 `set_project_trust`。这些通常是 operation，会发出 `operation_update`；界面应等待最终 response，并在失败时显示 `error.code`。

完整方法、参数校验、结果字段和错误码以 [`packages/coding-agent/src/rpc/protocol.ts`](https://github.com/qddidi/di-code/blob/master/packages/coding-agent/src/rpc/protocol.ts) 为准。Node.js 客户端可以直接使用公开的 `@di-code/coding-agent/rpc` 中的 `RpcClient`；浏览器客户端使用本指南的 HTTP/SSE envelope。

对 WebUI/SessionHost 请求应始终显式提供 `sessionId`；运行控制还要使用 `operation_update` 返回的 `runId`。服务端为旧版单 Session 调用方保留 active session 的缺省字段兼容，但该兼容不适用于多 Session 客户端，也不应作为新客户端的默认写法。

## 6. 工作区和 Session 隔离

服务端只向客户端返回不透明的 workspace/session/attachment ID，不返回绝对路径。启动目录默认是第一个工作区；其他工作区必须通过启动参数 `--workspace <path>` 授权，并在 trust store 中信任。

如果你实现工作区切换，使用 `/api/boot?workspaceId=<id>`、`/api/rpc?workspaceId=<id>`、`/api/events?workspaceId=<id>` 和 `/api/attachments?workspaceId=<id>`。不使用 `/api` 前缀时，`workspaceId` 也可以作为查询参数传给 `/rpc`、`/events` 和 `/attachments`。切换工作区后，应重新读取 Session、runtime、transcript 和 resources，不要复用旧 workspace 的缓存。

## 7. 断线、重连与状态恢复

SSE `ready` 返回的 `resumeToken` 默认 10 分钟有效，成功恢复后会轮换。重连请求带：

```http
X-Di-Code-Resume-Token: <上一次的 resumeToken>
Last-Event-ID: <最后处理的 sequence>
```

如果事件仍在服务端的有限重放窗口内，服务会补发缺失事件；如果窗口已经过期，会发送 `snapshot_required`。收到它时按以下顺序恢复：

```text
get_state -> get_transcript -> get_tree -> get_usage -> get_runtime
```

不要根据“最后一条看见的文本”猜测 Session 状态，也不要因为 SSE 重连而再次发送原来的 `prompt`。每个请求都使用唯一 `id`；重复使用同一个 id 时，服务端可能返回之前 operation 的结果。

客户端断开后，服务端会释放该客户端 principal 所拥有的 Session actor、MCP 连接和订阅；未结束的运行会被取消。重连会创建新的客户端上下文，因此应重新执行启动顺序并重新读取 Session、runtime 和资源快照。

## 8. 前端安全清单

- token 只放在内存或服务端，不放 localStorage、URL、日志和前端源码仓库；
- 只在可信本机或受控网络开放 `di-code-webui`，远程绑定必须设置 `DI_CODE_WEBUI_ALLOW_REMOTE=1`；
- 将 SSE 的 `event` 内容当作数据渲染，Markdown/文本进入 DOM 前使用框架的转义机制；
- 不把服务端返回的路径、工具参数或模型文本拼接成 shell 命令；
- 对 `BUSY`、`CANCELLED`、`NOT_FOUND`、`UNAUTHORIZED` 和 `snapshot_required` 提供明确 UI 状态；
- 记住 WebUI 不是沙箱：认证客户端可以触发当前工作区的文件工具和 shell。

内置 WebUI 的页面结构和 slot 扩展见 [WebUI 使用指南](使用指南.md) 与 [WebUI 自定义 UI](自定义UI.md)。
