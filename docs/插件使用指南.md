# di-code 插件使用指南

`di-code` 的插件运行在同一 Node.js 进程中。产品功能和第三方扩展都通过 `@di-code/plugin-runtime` 的 `Context`/`Fiber`，以及 `@di-code/plugin-loader` 的 namespace module 和 Composition Loader 装配；插件可在公开 registry、service 和 event 边界贡献能力。

## 发布包

第三方插件只依赖 `@di-code/plugin-sdk` 根入口，不能导入任意包的 `src`、`dist` 或未声明子路径。发布包必须是 ESM，并通过 `package.json` 的 `exports` 声明每个插件入口：

```json
{
  "name": "@acme/di-code-project-status",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    "./plugin": {
      "types": "./dist/plugin.d.ts",
      "import": "./dist/plugin.js"
    }
  },
  "dependencies": {
    "@di-code/plugin-sdk": "^0.1.7"
  },
  "diCode": {
    "apiVersion": 1,
    "plugins": ["./plugin"],
    "permissions": {
      "filesystem": "none",
      "network": [],
      "process": []
    }
  }
}
```

`diCode.plugins` 必须且只能列出一个由 package `exports` 声明、且解析后仍位于 package root 内的 entry。Loader 在 import 前验证该边界；default export 和私有深导入不支持。

## Namespace Entry

每个 entry 是一个 namespace module，必须导出非空 `name` 和 `apply`，且不能导出 `default`。`apiVersion` 省略或为 `1`，`version` 省略或为合法版本标识；发布包本身仍必须在 `diCode` 和 `package.json` 中提供版本信息。下面的完整示例选择显式导出这些 metadata，并注册一个由当前 Fiber 所有的服务：

```ts
import { createServiceKey, type PluginDefinition } from "@di-code/plugin-sdk";

export const projectStatusKey = createServiceKey<{ readonly label: string }>("acme.project-status");

export const apiVersion = 1 as const;
export const name = "acme.project-status";
export const version = "1.0.0";
export const apply: PluginDefinition["apply"] = (context) => {
	context.set(projectStatusKey, { label: "ready" });
};
```

`Context.set()`、服务注册、event subscription 和 `fiber.addDisposer()` 都归当前 Fiber 所有。异步 `apply` 完成前，其服务不会发布；setup 失败会回滚该 Fiber 的贡献。卸载会 abort signal、逆序执行 disposer 并移除贡献。插件应把 timer、listener、file handle、HTTP stream 和 child process 的关闭动作注册为 disposer。

`inject` 是 plugin definition 的依赖声明；Composition 的 `dependsOn` 负责 entry 的稳定拓扑顺序。服务可选时插件必须显式处理 `context.get()` 返回 `undefined`。不要在 handler 内重新实现 Provider/工具循环；模型-工具循环只能由 `@di-code/agent` 执行一次。

## Composition

Composition 是数据，不是 JavaScript。`@di-code/plugin-loader` 支持 JSON/YAML、受限 `$VAR`/`${VAR}` 值、稳定的 layer merge，以及以明确 entry id 为目标的 `insert`、`append`、`remove`、`replace`、`enable`、`disable`、`move` patch。它不会执行 shell substitution、命令替换或任意 `eval`。

```yaml
entries:
  - id: project-status
    name: "@acme/di-code-project-status/plugin"
    required: false
    dependsOn: ["Bootstrap"]
```

程序嵌入时，可用公开 Loader API 加载这份 entry：

```ts
import { createCompositionLoader } from "@di-code/plugin-loader";
import { createRootContext } from "@di-code/plugin-runtime";

const context = createRootContext({ mode: "test", trustedProject: true });
const loader = createCompositionLoader({
	context,
	entries: [
		{ id: "Bootstrap", name: "@di-code/builtins/bootstrap" },
		{
			id: "project-status",
			name: "@acme/di-code-project-status/plugin",
			dependsOn: ["Bootstrap"],
			required: false,
		},
	],
});

try {
	await loader.load();
} finally {
	await loader.dispose();
	await context.dispose();
}
```

当前 `di-code` CLI 使用内建 `base` 加一个 `interactive`、`print`、`json` 或 `rpc` mode composition，并将已启用的受管 package 加入 Loader。`--profile <print|json|interactive>` 选择 CLI profile；`--composition <path>` 将 JSON/YAML composition 作为最后一层应用。固定层级是 `base -> mode -> ~/.di-code/composition.yml -> <work-root>/.di-code/composition.yml -> --composition`。项目 composition 仅在项目已被 `--trust-project` 信任时读取；`--no-project-plugins` 为当前运行跳过它，但不影响用户托管 package。缺失的 user/project document 会忽略；格式错误或显式文件不可读取会终止启动并显示文件路径。disabled entry 不解析、不 import、不连接；required failure 会回滚先前 active entry 并阻止启动，optional failure 记录为 `skipped`。

## 安装和 Trust

受管插件使用 CLI 管理，安装目录位于 `~/.di-code/plugins/installed/`：

```powershell
di-code plugin install D:\work\my-plugin
di-code plugin install npm:@acme/di-code-project-status@1.0.0
di-code plugin install git:https://github.com/acme/di-code-project-status.git
di-code plugin list
di-code plugin disable project-status
di-code plugin enable project-status
di-code plugin remove project-status
```

`npm:` 安装固定使用 `npm install --ignore-scripts`。Loader 只解析 enabled registry 项；禁用项不会 import。安装通过 staging、managed-root 路径检查和 registry 原子替换完成，失败时恢复旧安装。registry 格式为 version `1`；install、update、enable、disable 和 remove 使用跨进程目录锁串行化，超时会明确失败，超过陈旧期限的遗留锁会在下一次写操作前回收。

project trust 只控制项目本地 Skills 和 MCP 配置是否可被加载。interactive TTY 可以询问，也可使用 `--trust-project` 或 `--untrust-project`；non-TTY 不等待输入。trust 不是插件权限升级，也不是 Node.js 沙箱。

## Capability、生命周期与安全

manifest `permissions` 是经 Loader 验证的审计声明：filesystem 枚举、HTTPS network URL 和精确 process command name 都有固定格式。runtime `CapabilityView` 由宿主 Context 提供；它同时要求 trusted project 和声明 capability，但 in-process code 仍拥有 Node.js 的进程权限。只安装可信 package；真正不可信代码必须移到独立进程桥接。

插件要自行验证不可信输入。文件路径必须检查根目录和 symlink 逃逸；网络 URL/host、命令参数、超时、输出上限和 abort signal 必须在能力服务或插件实现中明确处理。不要记录 `token`、`secret`、`authorization`、`api_key`、完整配置或 Provider 请求。`redactSensitiveText` 可用于诊断文本。

事件 handler 默认是观察者：错误会隔离并记录；只有显式 critical handler 才能阻止 event gate，且应设置 timeout 和取消处理。任何 handler 都不能作为工具授权门禁或第二个 Agent loop。

## 诊断

```powershell
di-code --trace-plugins
di-code --dump-composition
```

这两个命令按需挂载观测 entry，输出实际 Loader phase、owner Fiber、capability audit 和脱敏失败信息。它们不会输出 entry config、安装路径、凭据或 Provider 请求。

| 现象 | 检查 |
| --- | --- |
| package 无法安装 | `diCode.plugins`、`exports`、api version 与 package root 内 target 是否有效。 |
| entry 未加载 | `di-code plugin list` 的 enabled 状态；disabled 项不会解析或 import。 |
| entry skipped/failed | `dependsOn`、namespace `name`/`version`/`apply`、无 default export 和 optional/required 语义。 |
| 服务不可用 | 依赖 composition 是否提供服务，scope 是否 isolate，插件是否正确处理 optional service。 |
| trust 预期不符 | trust 只作用于项目 Skill/MCP，不决定受管插件 registry 的 enabled 状态。 |

相关 API：`@di-code/plugin-runtime` 提供生命周期和 service 基元；`@di-code/plugin-loader` 提供 manifest、Composition、trust 和安装；`@di-code/plugin-sdk` 是外部插件的稳定入口。
