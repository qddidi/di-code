# 插件使用指南

插件可以理解成“在 di-code 启动时一起加载的小程序”。它和 di-code 在同一个 Node.js 进程中运行，可以增加 Provider、工具、命令、Session 资源、TUI Host 或 WebUI 面板。

插件不会另起一套 Agent loop，也不能绕过宿主的参数校验、RPC schema 或工作区边界。插件加载后由一个 `Fiber` 管理；插件卸载时，这个 `Fiber` 会负责清理它注册的服务、事件监听器和其他资源。

## Session 级插件上下文

插件可以通过 `createSessionPluginFactory` 声明 Session 级资源，并将 factory 注册到宿主的 Session plugin registry。每个 Session ID 都会获得独立 scope；scope 提供 `sessionId`、`AbortSignal`、不可变 `capabilities`、Agent `hooks`、typed `events`/`projections` registry、动态 prompt sections、宿主绑定的 `appendEvent()` 和可选 `UserInteraction`，不暴露内部 `Agent`、`AgentSession`、`SessionManager`、文件句柄或 RPC transport。`appendEvent()` 使用当前 Session 的串行持久化队列；没有持久化宿主时会明确失败。Session 切换、关闭、创建失败和 Fiber 卸载都会调用幂等 `dispose()`；dispose 先 abort signal，再按逆序运行 disposer。同一 ID 的并发创建会以 `DUPLICATE` 错误拒绝，不同 Session 可以并发创建。

Session 扩展 UI 通过 `scope.extensions.registerBadge()` 和 `scope.extensions.registerUi()` 注册，宿主会将其聚合为只读 `SessionExtensionFacade`，并在 scope 卸载时自动清理。UI contribution 只能引用宿主白名单 `componentKey`，不会注入 HTML/JavaScript。

## 先看一个最小插件

下面这个插件只提供一个名为 `hello.message` 的服务。它不会改变界面，但足以说明插件的基本形状：一个 npm 包、一个 namespace entry，以及一个 `apply` 函数。

### 1. 创建插件目录

```text
hello-plugin/
  package.json
  plugin.js
```

`package.json`：

```json
{
  "name": "@acme/hello-plugin",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    "./plugin": "./plugin.js"
  },
  "dependencies": {
    "@di-code/plugin-sdk": "^0.1.8"
  },
  "diCode": {
    "apiVersion": 1,
    "plugins": ["./plugin"],
    "permissions": {
      "filesystem": "none",
      "network": [],
      "process": []
    }
  }
}
```

这里有三个容易漏掉的地方：

- `diCode.plugins` 必须且只能有一个 entry；
- `exports` 必须声明同名的 `"./plugin"`；
- 插件包使用 ESM，因此要写 `"type": "module"`。

插件 ID 默认从 npm 包名生成：`@acme/hello-plugin` 会得到 `hello-plugin`。ID 只能包含小写字母、数字和单连字符。

### 2. 编写入口文件

`plugin.js`：

```js
import { createServiceKey } from "@di-code/plugin-sdk";

export const apiVersion = 1;
export const name = "hello-plugin";
export const version = "1.0.0";

export const messageKey = createServiceKey("hello.message");

export function apply(context) {
	return context.set(messageKey, "Hello from my plugin!");
}
```

`apply` 在插件加载时调用。这里返回 `context.set(...)` 的清理函数，所以插件卸载后 `hello.message` 会自动移除。也可以显式接收第三个参数 `fiber`，用 `fiber.addDisposer(...)` 注册异步资源的清理逻辑。

插件入口必须是 namespace export，不能写 `export default`；必须导出非空的 `name` 和可调用的 `apply`。公共类型和工具从 `@di-code/plugin-sdk` 根入口导入，不要导入其他包的 `src`、`dist` 或未声明 subpath。

## 让插件出现在 WebUI 中

WebUI 扩展是声明式的：插件只声明“在哪个 slot 放哪个宿主组件”，不会把任意 HTML、URL 或 JavaScript 交给浏览器。下面的配置会在 WebUI 侧栏显示宿主已有的 `builtin.workspace-status` 组件。

在上面的 `package.json` 中加入 `diCode.web`：

```json
{
  "diCode": {
    "apiVersion": 1,
    "plugins": ["./plugin"],
    "permissions": {
      "filesystem": "none",
      "network": [],
      "process": []
    },
    "capabilities": { "ui": true },
    "web": {
      "protocolVersion": 1,
      "contributions": [
        {
          "id": "hello-sidebar",
          "slot": "app.sidebar",
          "version": 1,
          "order": 20,
          "capability": "ui",
          "componentKey": "builtin.workspace-status",
          "data": {
            "label": "插件已经加载"
          }
        }
      ]
    }
  }
}
```

可用 slot 包括 `app.sidebar`、`session.tree`、`conversation.node`、`conversation.tool`、`settings.panel`、`session.badge`、`session.controls`、`review.panel` 和 `composer.placeholder`。后四个 seat 用于状态徽章、控制入口、审阅面板和输入占位提示；它们使用版本化声明，TUI 与 WebUI 从同一个 Session/extension facade 消费。`componentKey` 必须是宿主白名单中的组件键；插件不能自定义一个 URL、HTML 或 JavaScript 让浏览器直接加载。`data` 只能包含字符串、数字、布尔值和 `null`，宿主会拒绝本地路径和凭据字段。

## 安装、启用和查看状态

在 di-code 项目中安装本地插件：

```powershell
di-code plugin install .\hello-plugin
```

安装后可以检查和管理状态：

```powershell
di-code plugin list
di-code plugin get hello-plugin
di-code plugin disable hello-plugin
di-code plugin enable hello-plugin
di-code plugin update hello-plugin
di-code plugin remove hello-plugin
```

也支持 npm 和 Git 来源：

```powershell
di-code plugin install npm:@acme/hello-plugin
di-code plugin install git:https://github.com/acme/hello-plugin.git
```

安装器会先在 staging 目录校验 manifest 和 entry，再替换受管插件目录。安装失败会回滚，npm 安装使用 `--ignore-scripts`。只有 enabled 插件才会被 Loader import；disabled 插件不会执行入口代码。

## 项目插件与信任

项目 `.di-code/composition.yml` 中的本地 entry 默认不会加载。确认项目内容可信后再启动：

```powershell
di-code --trust-project --interactive
```

信任只决定项目插件是否有资格被 import，不会授予额外文件、网络或进程权限，也不会创建操作系统沙箱。撤销信任后，重新启动或刷新 Composition 才会生效：

```powershell
di-code --untrust-project --interactive
```

直接启动交互 TUI（例如 `npm run dev`）时，如果检测到项目本地的 `composition.yml`、插件目录、Skills 或 MCP 配置且尚未作出信任决定，启动会先询问是否信任这些项目内容。回答 `y` 会持久化当前工作区的信任并继续加载；其他回答保持拒绝，项目本地内容不会执行。

交互 TUI 启动前会在终端输出资源摘要，列出项目/托管插件的 `active`、`failed`、`skipped` 或 `disabled` 状态、已加载 Skills、Skills/上下文诊断、已连接 MCP server 及其工具数量，以及 MCP 连接或发现失败。诊断文本会经过脱敏；没有项目资源时不输出空摘要。

WebUI 首次进入工作区时也会检查项目插件、Skills 和 MCP 配置。检测到尚未信任的项目资源会显示“Load project plugins and integrations?”弹窗；选择“Trust and load”会持久化当前工作区信任并加载资源，选择“Not now”则保持拒绝。设置 → Plugins 会同时列出托管插件与项目组合插件，并以颜色区分 `active`（绿）、`failed`（红）、`skipped`（黄）和 `disabled`（灰）状态；失败原因会直接显示。

排查插件为什么没有加载：

```powershell
di-code --trace-plugins
di-code --dump-composition
```

前者显示加载阶段、Fiber、能力审计和脱敏错误；后者显示最终 Composition tree，不包含配置值或密钥。

## 用 Composition 控制加载顺序

Composition 决定“加载哪些插件、用什么配置、先后顺序是什么”。例如，下面让 `hello-plugin` 在 `command-core` 之后加载，并传入一个配置值：

```yaml
entries:
  - id: command-core
    name: command-core
  - id: hello
    name: "@acme/hello-plugin/plugin"
    dependsOn: [command-core]
    config:
      greeting: "早上好"
```

这里的 `name` 是插件在 `exports` 中声明的公开入口；受管插件安装后，Loader 会自动解析为安装目录中的入口文件，通常不需要手写这一项。层级顺序是 `base -> mode -> user -> project -> explicit`。`dependsOn` 中的 entry 必须先处于 active 状态；缺失依赖、重复 ID 和循环依赖会阻止加载。`required: false` 可把一个可选插件的失败记录为 `skipped`，不会让整个启动失败。

插件的 `apply` 可以接收 Composition 配置：

```js
export function apply(context, config) {
	const greeting = typeof config?.greeting === "string" ? config.greeting : "你好";
	return context.set(messageKey, `${greeting}，来自插件`);
}
```

配置支持 `$ENV_VAR` 和 `${ENV_VAR}` 替换，但不执行 `$(...)` 或反引号中的 shell 命令。

## 注册工具或命令时怎么做

工具和命令由宿主提供 registry。插件需要在 Composition 中放在对应 registry entry 之后，并使用宿主公开的 registry key；不要自己复制一套 Agent loop。

概念上，工具注册包含四部分：名称、描述、JSON schema 和 `execute` 函数：

```ts
const dispose = toolRegistry.register(
	{
		name: "hello_echo",
		description: "返回传入的文本",
		parameters: {
			type: "object",
			properties: { text: { type: "string" } },
			required: ["text"],
			additionalProperties: false,
		},
		execute: async (_toolCallId, input, signal) => {
			signal?.throwIfAborted();
			return { text: input.text };
		},
	},
	fiber,
);
fiber.addDisposer(dispose);
```

这是注册流程的示意代码；具体 `toolRegistry`、`commandRegistry` 是否出现在运行时，取决于所选 Composition。工具仍必须自行校验路径、命令、超时、输出大小和取消信号。Agent 在真正执行前还会再次校验模型传入的参数。

贡献名称使用 `namespace:name` 作为全局标识。重复名称、保留名称和同名但不同 kind 的冲突都会失败。插件卸载时应通过 disposer 删除自己的注册，不能留下“幽灵”工具或命令。

### 接入图片输出 Provider

插件可以注册自己的 Provider 和模型来接入生图服务。Provider 在流中发出 `StreamEvent` 的原子 `image` 事件，事件中的 `image` 使用 `mimeType` 和不带 `data:` 前缀的 Base64 数据；Agent 会把它保留在最终 `AssistantMessage.content`，Session、RPC 和 WebUI 会继续传递并显示在助手聊天气泡中。Provider 应在发出事件前完成远程图片下载、格式校验、大小限制和取消处理，不要把带凭据的 URL 写入 Session 或日志。

## 生命周期：记住清理资源

插件生命周期大致如下：

```text
pending -> loading -> active -> unloading -> disposed
                    \-> failed
```

推荐把每个资源的清理函数紧挨着创建代码注册：

```ts
export function apply(context, _config, fiber) {
	const timer = setInterval(() => context.logger.debug("heartbeat"), 10_000);
	fiber.addDisposer(() => clearInterval(timer));

	const unsubscribe = context.events.subscribe((event) => {
		context.logger.info(`收到事件: ${event.type}`);
	});
	fiber.addDisposer(unsubscribe);
}
```

`fiber.signal` 会在卸载时 abort。异步请求、子进程、文件句柄、MCP 连接和临时文件都要监听这个 signal，并覆盖成功、失败、取消和重复 dispose 路径。required 插件失败时，Loader 会回滚已经激活的前置 entry；optional 插件失败时会留下 `skipped` 诊断。

## 权限和安全边界

manifest 中的 `permissions` 描述插件可能影响的范围，`capabilities` 描述插件向宿主声明的能力。例如：

```json
{
  "permissions": {
    "filesystem": "read-project",
    "network": ["https://api.example.com"],
    "process": ["git"]
  },
  "capabilities": {
    "filesystem": true,
    "network": true
  }
}
```

可选的文件范围是 `none`、`read-project`、`workspace`、`user` 和 `unrestricted`；网络只接受绝对 HTTPS URL；进程权限填写精确命令名。`permissions` 用于 manifest 声明、格式校验和审计；`capabilities` 用于宿主的 capability view 检查。它们都**不是操作系统级沙箱**，也不会阻止插件代码自行访问文件、网络或进程。插件代码仍然运行在宿主进程中，因此只安装可信来源，并在实现中自行做输入校验、路径边界检查、超时、取消和输出限制。

如果 `composition.yml` 直接指向本地模块（而不是通过受管插件 manifest 安装），能力要在模块导出中声明：`export const capabilities = { process: true }`，或放进导出的 `plugin` 对象。设置页的项目插件能力列表会读取已加载 Fiber 的声明；未信任或未加载的项目插件无法推断能力，因此会显示“未声明能力”。

不要把 API key、token、`Authorization` header、完整请求体或用户敏感内容写入日志、异常、Web contribution 或 Session record。插件 logger 会对常见凭据字段做脱敏，但插件仍应尽量避免收集这些数据。

## 常见问题

| 现象 | 优先检查 |
| --- | --- |
| `plugin install` 失败 | `diCode.apiVersion`、`diCode.plugins` 是否只有一项，`exports` 是否声明同名 entry |
| 插件显示 `disabled` 或 `pending` | 启停操作会在下次运行时重载后生效；重新启动后检查状态 |
| 项目插件显示 `skipped` | 使用 `--trust-project`，确认当前目录是预期工作区 |
| `Required entry ... failed` | 查看 `--trace-plugins`，检查依赖顺序、入口导出和 `apply` 异常 |
| Web 面板不显示 | 检查 `protocolVersion`、slot、`componentKey`、`capabilities.ui` 和重复 `id` |
| 工具或命令找不到 | 确认对应 registry 已在 Composition 中加载，并且插件 entry 的 `dependsOn` 正确 |

更多源码导航和插件开发测试方法见 [开发教程](开发教程.md)；Web slot 的完整声明见 [WebUI 自定义 UI](webui/自定义UI.md)。

## Agent 生命周期 hook

插件 SDK 导出版本化的 `AgentHookRegistration`。hook 必须声明 `kind`、`phase` 和可选 `timeoutMs`/`onError`，宿主按注册顺序串行调用并传入 `AbortSignal`。观察型 hook 只读取事件；`kind: "modifier"` 仅可用于 `pre_step`，通过返回新的 `assembly` 或 `skip`/`abort` decision 影响当前步骤，不能修改共享请求对象。可用阶段为 `request_prepare`、`pre_step`、`request_accept`、`tool_execute_before`、`step_complete`、`turn_complete`、`failed` 和 `cancelled`。hook 失败、取消和超时都由宿主收敛到当前 Agent 终态，监听器 disposer 幂等，插件不能启动第二套 Agent loop。

## 动态 Prompt section

Session scope 的 `promptSections` registry 允许插件按当前快照生成 system prompt。注册项包含唯一 `name`、有限的 `order`、非空 `owner` 和 `generate(context)`；同名注册拒绝，同序按注册顺序排列，空文本跳过。每次 Provider request 都重新读取 Agent/Session 快照；生成异常或取消会终止当前请求，旧 `systemPrompt` 仍位于所有 section 之前。注册返回的 disposer 必须在插件卸载时调用，宿主也会在 Session scope dispose 前清空该 registry。
## Typed Session event 与 projection

插件可通过 `@di-code/plugin-sdk` 的 `createSessionEventRegistry()` 声明命名空间事件、schema 版本、校验器和迁移函数，再由宿主 `SessionManager.appendEvent()` 追加。追加操作进入 Session 串行队列并受文件锁、`AbortSignal` 和 256 KiB payload 上限约束。`createSessionProjectionRegistry()` 从完整事件日志纯回放状态，因此 Session 恢复、分支、压缩和冷读都不依赖内存镜像。未注册事件、损坏 payload 和迁移失败必须保留为诊断；事件中禁止写入凭据、完整请求体或敏感用户内容。
### Session 级工具策略

每个 Session 都有独立的 `ToolPolicy`。工具目录保持稳定，宿主在执行前强制授权；因此 prompt 不能绕过策略。策略状态可读取宿主 projection 和插件状态，模式切换以 `di-code.tool-policy:mode_changed` 事件写入 Session，恢复或 fork 时从事件重放。`read_only` 会拒绝 `write`、`edit`、`bash` 等 mutation tool，并返回 `POLICY_DENIED`；取消、超时和 dispose 使用不同错误码。该边界不会放宽文件路径、symlink、shell 参数、输出上限或取消检查。
# UserInteraction

插件通过 SDK 的 `UserInteraction` facade 请求用户输入或审批，不直接访问 TUI、WebUI、RPC transport 或 Session。请求必须带稳定的 `requestId`，工具审批可附带 `toolCallId` 和 `intent: "tool-approval"`。支持单问题、多问题、选项、自由文本、取消和超时；结果只使用结构化字段（`approved`、`value`、`values`、`feedback`），UI token、cookie、key 等内部数据不得进入 Session。

没有可用 UI channel 时请求会快速返回 `INTERACTION_UNAVAILABLE`；审批保持拒绝安全默认。RPC 客户端先协商 `interaction_request`，再通过 `respond_interaction` 回答；重复回答不会改变第一次结果。短暂断线不会丢弃 pending 请求：客户端在重连或收到 `snapshot_required` 后从 `get_state.state.interactions` 恢复它；取消、超时和插件卸载才会结束请求。

## Plan Mode 参考插件

`@di-code/plan-mode` 是基于上述扩展点的独立参考实现。它提供 `/plan [message]`、`/plan off`、可回放的 `plan/mode` 事件和 `{ active, pending }` projection，并注册动态 `plan:policy` section 与稳定的 `exit_plan_mode` 工具。审阅通过 `intent: "plan-review"` 展示完整 Markdown 计划；Approve 退出，Keep planning 返回反馈，取消保持计划状态。

插件只通过 `PlanModeAdapter` 调用宿主的 `SessionManager.appendEvent()`，不会直接读写 Session JSONL。使用 `createPlanToolPolicy()` 组合宿主策略后，`write`、`edit` 和 `bash` 在 plan mode 下会在执行边界返回 `POLICY_DENIED`。迁移、兼容矩阵和安全审计见 `docs/插件/Plan Mode迁移指南.md`、`Plan Mode兼容矩阵.md` 与 `Plan Mode安全审计.md`。
