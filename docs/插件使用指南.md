# 插件使用指南

插件可以理解成“在 di-code 启动时一起加载的小程序”。它和 di-code 在同一个 Node.js 进程中运行，可以增加 Provider、工具、命令、Session 资源、TUI Host 或 WebUI 面板。

插件不会另起一套 Agent loop，也不能绕过宿主的参数校验、RPC schema 或工作区边界。插件加载后由一个 `Fiber` 管理；插件卸载时，这个 `Fiber` 会负责清理它注册的服务、事件监听器和其他资源。

## 先看一个最小插件

下面这个插件只提供一个名为 `hello.message` 的服务。它不会改变界面，但足以说明插件的基本形状：一个 npm 包、一个 namespace entry，以及一个 `apply` 函数。

### 1. 创建插件目录

```text
hello-plugin/
  package.json
  plugin.js
```

`package.json`：

```json
{
  "name": "@acme/hello-plugin",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    "./plugin": "./plugin.js"
  },
  "dependencies": {
    "@di-code/plugin-sdk": "^0.1.8"
  },
  "diCode": {
    "apiVersion": 1,
    "plugins": ["./plugin"],
    "permissions": {
      "filesystem": "none",
      "network": [],
      "process": []
    }
  }
}
```

这里有三个容易漏掉的地方：

- `diCode.plugins` 必须且只能有一个 entry；
- `exports` 必须声明同名的 `"./plugin"`；
- 插件包使用 ESM，因此要写 `"type": "module"`。

插件 ID 默认从 npm 包名生成：`@acme/hello-plugin` 会得到 `hello-plugin`。ID 只能包含小写字母、数字和单连字符。

### 2. 编写入口文件

`plugin.js`：

```js
import { createServiceKey } from "@di-code/plugin-sdk";

export const apiVersion = 1;
export const name = "hello-plugin";
export const version = "1.0.0";

export const messageKey = createServiceKey("hello.message");

export function apply(context) {
	return context.set(messageKey, "Hello from my plugin!");
}
```

`apply` 在插件加载时调用。这里返回 `context.set(...)` 的清理函数，所以插件卸载后 `hello.message` 会自动移除。也可以显式接收第三个参数 `fiber`，用 `fiber.addDisposer(...)` 注册异步资源的清理逻辑。

插件入口必须是 namespace export，不能写 `export default`；必须导出非空的 `name` 和可调用的 `apply`。公共类型和工具从 `@di-code/plugin-sdk` 根入口导入，不要导入其他包的 `src`、`dist` 或未声明 subpath。

## 让插件出现在 WebUI 中

WebUI 扩展是声明式的：插件只声明“在哪个 slot 放哪个宿主组件”，不会把任意 HTML、URL 或 JavaScript 交给浏览器。下面的配置会在 WebUI 侧栏显示宿主已有的 `builtin.workspace-status` 组件。

在上面的 `package.json` 中加入 `diCode.web`：

```json
{
  "diCode": {
    "apiVersion": 1,
    "plugins": ["./plugin"],
    "permissions": {
      "filesystem": "none",
      "network": [],
      "process": []
    },
    "capabilities": { "ui": true },
    "web": {
      "protocolVersion": 1,
      "contributions": [
        {
          "id": "hello-sidebar",
          "slot": "app.sidebar",
          "version": 1,
          "order": 20,
          "capability": "ui",
          "componentKey": "builtin.workspace-status",
          "data": {
            "label": "插件已经加载"
          }
        }
      ]
    }
  }
}
```

可用 slot 包括 `app.sidebar`、`session.tree`、`conversation.node`、`conversation.tool` 和 `settings.panel`。`componentKey` 必须是宿主白名单中的组件键；插件不能自定义一个 URL 让浏览器直接加载。`data` 只能包含字符串、数字、布尔值和 `null`。

## 安装、启用和查看状态

在 di-code 项目中安装本地插件：

```powershell
di-code plugin install .\hello-plugin
```

安装后可以检查和管理状态：

```powershell
di-code plugin list
di-code plugin get hello-plugin
di-code plugin disable hello-plugin
di-code plugin enable hello-plugin
di-code plugin update hello-plugin
di-code plugin remove hello-plugin
```

也支持 npm 和 Git 来源：

```powershell
di-code plugin install npm:@acme/hello-plugin
di-code plugin install git:https://github.com/acme/hello-plugin.git
```

安装器会先在 staging 目录校验 manifest、entry 和 Web bundle，再替换受管插件目录。安装失败会回滚，npm 安装使用 `--ignore-scripts`。只有 enabled 插件才会被 Loader import；disabled 插件不会执行入口代码。

## 项目插件与信任

项目 `.di-code/composition.yml` 中的本地 entry 默认不会加载。确认项目内容可信后再启动：

```powershell
di-code --trust-project --interactive
```

信任只决定项目插件是否有资格被 import，不会授予额外文件、网络或进程权限，也不会创建操作系统沙箱。撤销信任后，重新启动或刷新 Composition 才会生效：

```powershell
di-code --untrust-project --interactive
```

排查插件为什么没有加载：

```powershell
di-code --trace-plugins
di-code --dump-composition
```

前者显示加载阶段、Fiber、能力审计和脱敏错误；后者显示最终 Composition tree，不包含配置值或密钥。

## 用 Composition 控制加载顺序

Composition 决定“加载哪些插件、用什么配置、先后顺序是什么”。例如，下面让 `hello-plugin` 在 `command-core` 之后加载，并传入一个配置值：

```yaml
entries:
  - id: command-core
    name: command-core
  - id: hello
    name: "@acme/hello-plugin/plugin"
    dependsOn: [command-core]
    config:
      greeting: "早上好"
```

这里的 `name` 是插件在 `exports` 中声明的公开入口；受管插件安装后，Loader 会自动解析为安装目录中的入口文件，通常不需要手写这一项。层级顺序是 `base -> mode -> user -> project -> explicit`。`dependsOn` 中的 entry 必须先处于 active 状态；缺失依赖、重复 ID 和循环依赖会阻止加载。`required: false` 可把一个可选插件的失败记录为 `skipped`，不会让整个启动失败。

插件的 `apply` 可以接收 Composition 配置：

```js
export function apply(context, config) {
	const greeting = typeof config?.greeting === "string" ? config.greeting : "你好";
	return context.set(messageKey, `${greeting}，来自插件`);
}
```

配置支持 `$ENV_VAR` 和 `${ENV_VAR}` 替换，但不执行 `$(...)` 或反引号中的 shell 命令。

## 注册工具或命令时怎么做

工具和命令由宿主提供 registry。插件需要在 Composition 中放在对应 registry entry 之后，并使用宿主公开的 registry key；不要自己复制一套 Agent loop。

概念上，工具注册包含四部分：名称、描述、JSON schema 和 `execute` 函数：

```ts
const dispose = toolRegistry.register(
	{
		name: "hello_echo",
		description: "返回传入的文本",
		parameters: {
			type: "object",
			properties: { text: { type: "string" } },
			required: ["text"],
			additionalProperties: false,
		},
		execute: async (_toolCallId, input, signal) => {
			signal?.throwIfAborted();
			return { text: input.text };
		},
	},
	fiber,
);
fiber.addDisposer(dispose);
```

这是注册流程的示意代码；具体 `toolRegistry`、`commandRegistry` 是否出现在运行时，取决于所选 Composition。工具仍必须自行校验路径、命令、超时、输出大小和取消信号。Agent 在真正执行前还会再次校验模型传入的参数。

贡献名称使用 `namespace:name` 作为全局标识。重复名称、保留名称和同名但不同 kind 的冲突都会失败。插件卸载时应通过 disposer 删除自己的注册，不能留下“幽灵”工具或命令。

## 生命周期：记住清理资源

插件生命周期大致如下：

```text
pending -> loading -> active -> unloading -> disposed
                    \-> failed
```

推荐把每个资源的清理函数紧挨着创建代码注册：

```ts
export function apply(context, _config, fiber) {
	const timer = setInterval(() => context.logger.debug("heartbeat"), 10_000);
	fiber.addDisposer(() => clearInterval(timer));

	const unsubscribe = context.events.subscribe((event) => {
		context.logger.info(`收到事件: ${event.type}`);
	});
	fiber.addDisposer(unsubscribe);
}
```

`fiber.signal` 会在卸载时 abort。异步请求、子进程、文件句柄、MCP 连接和临时文件都要监听这个 signal，并覆盖成功、失败、取消和重复 dispose 路径。required 插件失败时，Loader 会回滚已经激活的前置 entry；optional 插件失败时会留下 `skipped` 诊断。

## 权限和安全边界

manifest 中的 `permissions` 描述插件可能影响的范围，`capabilities` 描述插件向宿主声明的能力。例如：

```json
{
  "permissions": {
    "filesystem": "read-project",
    "network": ["https://api.example.com"],
    "process": ["git"]
  },
  "capabilities": {
    "filesystem": true,
    "network": true
  }
}
```

可选的文件范围是 `none`、`read-project`、`workspace`、`user` 和 `unrestricted`；网络只接受绝对 HTTPS URL；进程权限填写精确命令名。这些字段用于加载决策、能力检查和审计，**不是操作系统级沙箱**。插件代码仍然运行在宿主进程中，因此只安装可信来源，并在实现中自行做输入校验、路径边界检查、超时、取消和输出限制。

不要把 API key、token、`Authorization` header、完整请求体或用户敏感内容写入日志、异常、Web contribution 或 Session record。插件 logger 会对常见凭据字段做脱敏，但插件仍应尽量避免收集这些数据。

## 常见问题

| 现象 | 优先检查 |
| --- | --- |
| `plugin install` 失败 | `diCode.apiVersion`、`diCode.plugins` 是否只有一项，`exports` 是否声明同名 entry |
| 插件显示 `disabled` | 执行 `di-code plugin enable <id>`，再重新启动 |
| 项目插件显示 `skipped` | 使用 `--trust-project`，确认当前目录是预期工作区 |
| `Required entry ... failed` | 查看 `--trace-plugins`，检查依赖顺序、入口导出和 `apply` 异常 |
| Web 面板不显示 | 检查 `protocolVersion`、slot、`componentKey`、`capabilities.ui` 和重复 `id` |
| 工具或命令找不到 | 确认对应 registry 已在 Composition 中加载，并且插件 entry 的 `dependsOn` 正确 |

更多源码导航和插件开发测试方法见 [开发教程](开发教程.md)；Web slot 的完整声明见 [WebUI 自定义 UI](webui/自定义UI.md)。
